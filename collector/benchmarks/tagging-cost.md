# Стоимость и скорость тегирования статьи (Gemma)

Раздел: collector
Дата: 2026-10-24 · Версия кода: рефакторинг на семь разделов (до первого коммита) · Автор: ИИ-агент по заданию

## Что измеряем
Сколько токенов и времени занимает тегирование одной статьи по фиксированному словарю (525 тегов) и справляется ли воркер с потоком новостей в рамках бюджета 500 ₽ в сутки.

## Метрика
Токены запроса и ответа (из `usage`), секунды на статью. Меньше лучше. Производительность в сутки = 86 400 с ÷ секунд на статью (один воркер).

## Данные и окружение
Живой шлюз организаторов, модель `google/gemma-4-26b-a4b-it`, одна синтетическая статья из двух предложений (тест `TestLiveWorker`, `LIVE_LLM_TEST=1`).

## Сравниваемые методы
Один вариант: весь словарь с правилами и схемой результата в системном сообщении, текст статьи в сообщении пользователя.

## Результаты
| Метрика | Значение |
|---|---|
| Токены запроса | 57 650 |
| Токены ответа | 112 |
| Время одного запроса | около 99 с |
| Статей в сутки одним воркером | около 870 |

## Вывод
Словарь составляет почти весь запрос, поэтому цена не зависит от длины статьи. Воркер идёт по очереди подряд, при исчерпании бюджета встаёт на паузу до 03:00 по Москве. Корпус в сотни тысяч статей такой схемой не разметить; без изменения схемы (сжатие словаря, выборочное тегирование) включать `LLM_ENABLED=true` на всём потоке дорого. Решение пока не принято: флаг `LLM_ENABLED` позволяет собирать без расходов.

## Ограничения
Один запрос, одна статья; цены шлюза в замере не снимались, только токены.

## Как воспроизвести
```bash
cd collector && TEST_DATABASE_URL=… LIVE_LLM_TEST=1 LLM_API_KEY=… LLM_MODEL=google/gemma-4-26b-a4b-it go test -count=1 -v -run TestLiveWorker ./internal/news/tagging
```

## Прогон 2026-10-25: предотбор географии (#18, шаг 1)

Ветка `collector/geo-prefilter`. Гипотеза: география — около 75 % словаря; если показывать модели только кандидатов статьи, вход сократится в несколько раз.

**Метрика:** токены запроса из `usage`, одна и та же модель и статья (меньше лучше); для предотбора — доля статей, где кандидаты найдены кодом без вызова модели.

**Данные:** живой шлюз, `google/gemma-4-26b-a4b-it`, синтетическая статья из `TestLiveWorker` («Банк России сообщил о сохранении ключевой ставки…»). Для предотбора — 3 000 случайных статей локального корпуса (заголовок + первые 300 знаков текста, без Google News).

| Вариант | Тегов в запросе | Токены запроса | Токены ответа |
|---|---|---|---|
| Весь словарь (`news-tags-v1`) | 525 | 57 650 | 76 |
| Предотбор географии (`news-tags-v2`) | 163 | 17 267 | 76 |

Вход сократился на 70 % (в 3,3 раза). Код нашёл кандидатов у 782 из 3 000 статей (26 %); для остальных нужен пакетный вопрос модели: 214 токенов на три статьи в живом тесте `TestLivePlaces` (до 30 статей в запросе).

**Вывод:** шаг 1 из #18 даёт −70 % на запрос тегирования; цель «на порядок» требует ещё сжатия описаний остальных тегов или нескольких статей в одном запросе.

**Ограничения:** одна статья в замере токенов; точность тегов на размеченном наборе не измерялась; рубли не считались (цена шлюза неизвестна). В обоих вариантах Gemma вернула ответ, который не прошёл проверку JSON («tagging response requires a JSON object»), — это не связано с предотбором; с `deepseek/deepseek-v4.1-flash` (модель в `.env`) `TestLiveWorker` прошёл: 18 684 токена запроса.

**Как воспроизвести:**
```bash
cd collector && LIVE_LLM_TEST=1 ENV_FILE=../.env TEST_DATABASE_URL=… go test -count=1 -v -run 'TestLiveWorker$|TestLivePlaces' ./internal/news/tagging
```
