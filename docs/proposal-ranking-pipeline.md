# Предложение: конвейер отбора новостей под профиль пользователя

Статус: **черновик на обсуждение командой**, не утверждён. Затрагивает модули тегирования (Саша), графа (Тимофей) и ранжирования (Лев).

## Зачем

Пользователь не описывает себя текстом: при входе известны только роль (из фиксированного списка), ОКВЭД, регион/город, размер компании и продукты банка. Нужно по этим параметрам выбрать из недельного потока новостей то, что влияет на его решения, и передать это LLM для выводов.

## Коротко о результате экспериментов

Проверено на 2 008 сюжетах (одна неделя, 20 источников) и 16 синтетических профилях. Оценка — по размеченной релевантности и по качеству итоговой записки (слепое сравнение, 0–10).

| Вариант | Итоговая оценка /10 |
|---|---|
| **Предлагаемый конвейер (с диверсификацией по аспектам)** | **6,2** |
| Тот же конвейер без диверсификации | 5,5 |
| Отбор только по графу отраслей (BFS по тегам) | 3,7 |
| Гибрид «граф → эмбеддинги» | 4,1 |
| 5 лучших по эмбеддингам + 5 лучших по графу | 5,7 |

Главные выводы:
1. **Решает представление профиля.** Если искать по самим параметрам («финдиректор; грузоперевозки; Сибирь»), качество поиска низкое (nDCG@10 = 0,12). Если один раз развернуть параметры в ~20 «информационных потребностей» («как изменение ключевой ставки повлияет на стоимость лизинга грузового парка?»), — 0,53, в 4 раза выше.
2. **Граф как ранжировщик проигрывает** эмбеддингам: при 18 разделах ОКВЭД слишком много равных оценок. Граф полезен как **объяснение** («почему вам это показано»), а не как основной отбор.
3. **Разнообразие важнее точности.** Диверсификация по аспектам профиля и список из 40 дополнительных заголовков дают наибольший прирост. Переранжирование кросс-энкодером не помогает.
4. **Поиск близок к потолку** (~97 % важных сюжетов в топ-50). Дальнейший резерв — в модели, которая пишет выводы, а не в поиске.

## Предлагаемый конвейер

### Пошагово, простыми словами

1. **Карточка события (один раз на новость).** LLM читает заголовок и начало новости и заполняет карточку по фиксированному словарю: что случилось, кто участники, регионы, затронутые разделы ОКВЭД, тип события, механизм влияния, горизонт, жанр (новость/аналитика/мнение) и пары «причина → следствие» (например, «рост цен на топливо → H: рост издержек»).
2. **Стандартный ключ и векторы новости.** Из карточки без LLM собирается строка-ключ по шаблону «<раздел ОКВЭД>: <событие> → <эффект, для кого>», например «Транспортировка и хранение: спрос на автоперевозки вырос на 20% → рост спроса для: Транспортировка и хранение». Считаются два эмбеддинга: по ключу (основной) и по исходному тексту (вспомогательный, ловит имена, цифры и формулировки).
3. **Профиль (один раз на комбинацию параметров, кэшируется).** Из параметров входа собирается набор запросов:
   - фиксированные шаблоны по роли (например, для главбуха — «налоги, НДС, отчётность»);
   - ~20 «информационных потребностей», которые LLM пишет по параметрам;
   - 5–8 взвешенных аспектов (группы потребностей: «ставки и кредит», «топливо и издержки» …).
4. **Поиск.** Каждый запрос профиля и каждая новость — точки в одном пространстве; близость = косинусное сходство. Сходства каждого запроса нормируются по всему корпусу (z-оценка), чтобы общие запросы («ставка ЦБ») не забивали специфичные. Оценка новости — среднее трёх лучших совпадений с запросами, максимум по двум её векторам (ключ, исходный текст).
5. **Диверсификация.** Из топ-100 жадно выбираются 10 новостей так, чтобы покрыть аспекты профиля пропорционально их весам (алгоритм xQuAD), а не набрать 10 почти одинаковых.
6. **Пакет для LLM.** 10 карточек (дубли одной темы склеиваются), к каждой — до 4 связанных новостей недели, плюс 40 однострочных заголовков «прочее важное».
7. **Выводы.** LLM с «плейбуком» роли (стандартные правила решений с проверкой направления эффекта) пишет: решения сейчас, что мониторить, что сознательно игнорировать. Каждое утверждение ссылается на ID новости.
8. **Проверка ссылок.** После генерации ID новостей сверяются с пакетом; несуществующие ссылки удаляются или помечаются (в экспериментах модель выдумывала 1–11 % ID).
9. **Объяснение через граф.** Для каждой показанной новости по парам «причина → следствие» строится путь «ваш раздел ОКВЭД → раздел события», который показывается пользователю как ответ на «почему мне это показали».

### Что считается когда

| Этап | Когда | Стоимость |
|---|---|---|
| Карточка события | один раз на новость | 1 вызов LLM на ~40 новостей |
| Профиль (потребности, аспекты) | один раз на комбинацию параметров | 1 вызов LLM, кэш |
| Поиск и диверсификация | на каждого пользователя в день | только CPU |
| Выводы | на каждого пользователя в день | 1 вызов LLM, ~10 тыс. входных токенов |

## Что меняется для модулей

- **Тегирование (Саша):** карточка события расширяет текущий формат тегов: добавляются поля «механизм», «горизонт», «жанр» и пары «причина → следствие». Словарь значений — фиксированный (разделы ОКВЭД A–R, 17 типов событий, 14 типов эффектов, регионы). Предлагается обсудить его как вариант словаря.
- **Граф (Тимофей):** граф строится из пар «причина → следствие» и используется для объяснений и как необязательный источник «резервных» мест в выдаче, а не как основной ранжировщик.
- **Ранжирование (Лев):** BFS по графу заменяется на поиск по эмбеддингам с развёрнутым профилем и диверсификацией.

## Дополнение: стандартный ключ новости и выбор запросов (эксперимент от 22.10)

Что даёт каждый вектор новости (запросы — шаблоны роли + потребности от LLM):

| Векторы новости | α-nDCG | nDCG@10 (dev) | nDCG@10 (test) |
|---|---|---|---|
| только исходный текст | 0,37 | 0,39 | 0,49 |
| только текст карточки | 0,45 | 0,46 | 0,51 |
| только стандартный ключ | 0,50 | 0,49 | 0,53 |
| **ключ + исходный текст** | **0,51** | **0,52** | **0,56** |
| ключ + исходный текст, с z-нормировкой запросов | 0,49 | 0,55 | 0,55 |

Выводы:
- Стандартный ключ — лучший одиночный вектор, бесплатно (собирается из карточки без LLM). Исходный текст сам по себе слабее всех, но как второй вектор добавляет +0,01…0,03. Отдельный вектор по тексту карточки после появления ключа не нужен.
- **Запросы из готовых блоков не работают.** Проверена библиотека блоков (роль / раздел ОКВЭД / регион / продукт), собираемая по параметрам без LLM: α-nDCG 0,17–0,24 против 0,49–0,51 у потребностей от LLM. Блоки слишком общие («ставка выросла») и совпадают с макроновостями у всех пользователей; теряется пересечение «роль × отрасль × продукт».
- **Как всё же обойтись без LLM на пользователя:** комбинаций параметров конечное число (~2–3 тыс.). Потребности генерируются один раз на комбинацию (заранее или при первом входе) и кэшируются; при входе пользователь получает готовый набор из этого конечного списка.

## Открытые вопросы к команде

1. Принимаем ли роль графа как слоя объяснений, а не ранжирования?
2. Согласуем ли словарь карточки события (раздел «Тегирование» выше)?
3. Какой эмбеддер берём: bge-m3 (проверен целиком) или multilingual-e5-large-instruct (лучше в офлайн-тесте, +0,07 nDCG, но не проверен на итоговых записках)?
4. Какая одобренная модель пишет выводы? Эксперименты шли на модели-заменителе; следующий шаг — сравнить Qwen3.6, GLM-5.3-Flash и DeepSeek-V4.1-Flash на этом конвейере.

## Ограничения проверки

Одна неделя новостей, 16 синтетических профилей; разметка, извлечение ключевых пунктов и оценка выполнены моделями одного семейства (не из одобренного списка, только для оценки). Абсолютные оценки с одобренными моделями будут другими; сравнительные выводы (профиль важнее всего, граф хуже как ранжировщик, разнообразие помогает) ожидаемо переносятся.
