# 2. Агенты (Python-сервис `agents`)

Единственное место, где Python-код обращается к LLM организаторов (Go-тегирование в `collector` — отдельное исключение). Код: [agents/app.py](../agents/app.py) (шлюз, агенты и HTTP) и [agents/prompts/](../agents/prompts/). Задача сервиса: принять имя агента и данные, собрать запрос, вызвать нужную модель, вернуть проверенный JSON.

## Что делает, шаг за шагом

1. Вызывающий сервис шлёт `POST /agents/{имя}` с `{"input": {...}}`.
2. Сервис проверяет, что агент существует (иначе 404) и что есть все обязательные поля (иначе 422).
3. Шаблон запроса `agents/prompts/<имя>.md` заполняется данными: подставляются только `{поля}` из входа, фигурные скобки примеров JSON остаются как есть.
4. Запрос уходит модели потоковым вызовом (длинные ответы с рассуждениями рвут обычные соединения): сначала основной шлюз, при ошибке резервный. Модель должна быть в списке разрешённых организаторами, иначе вызов отклоняется до сети.
5. Из ответа берётся JSON-объект. Если он пустой, обрезан или в нём нет нужного ключа, запрос повторяется (до 3 раз); если модель потратила весь лимит токенов на рассуждения, лимит следующей попытки увеличивается.
6. Результат приводится к ожидаемому виду (например, `pick` оставляет только известные номера) и возвращается вместе с расходом: вызовы, токены, стоимость.

## Агенты

| Имя | Модель | Вход | Выход | Кто вызывает |
|---|---|---|---|---|
| `queries` | DeepSeek-V4.1-Flash | `company`, `line`, `region?` | блоки поисковых запросов (11 блоков, ключ `company_self` обязателен) | news_search |

| `hyde` | DeepSeek | `company`, `line`, `region?` | `{"headlines": [40 заголовков]}` | news_search |
| `pick` | GLM-5.3-Flash | `company`, `line`, `candidates`, `top?` | `{"top": [номера]}` | news_search (`dense_llm`) |
| `analytics_step` | Gemma 4 26B A4B | `company`, `kinds`, `title`, `thoughts`, `materials`, `facts?`, `sphere?`, `text?` | одно рассуждение с цитатой | analytics |
| `decision` | DeepSeek | `role`, `moves`, `title`, `notes`, `sphere?` | решение с рисками | analytics |
| `verify` | Qwen3.6 35B | `claims` | `{"verdicts": [...]}` | analytics |
| `reply` | DeepSeek | `question`, `title?`, `text?`, `risks?`, `facts?` | ответ на вопрос по разбору | analytics |
| `alfa_page` | Qwen3-VL 30B | `page`, `text?`, `images?` | тезисы страницы PDF | `python -m analytics.alfa` |

Список с моделями и полями отдаёт `GET /agents`.

## Как добавить агента

1. Положите шаблон в `agents/prompts/<имя>.md` с плейсхолдерами `{поле}`.
2. Добавьте запись в `AGENTS` в [app.py](../agents/app.py): модель, обязательные поля, функцию сборки запроса, ключ, который должен быть в ответе, лимит токенов.
3. Допишите вход в тест `test_every_agent_builds_a_prompt_from_minimal_input`.

## Как пользоваться из другого сервиса

```python
from agents.client import Agents
agents = Agents()                      # адрес берётся из AGENTS_URL
out = agents.run("hyde", {"company": "Делимобиль", "line": "Закупки"})
print(out["headlines"][:3], agents.cost)   # agents.cost, agents.tokens, agents.calls копятся по экземпляру
```

`agents/client.py` копируется в образы news_search и analytics рядом с их кодом.

## Настройки и проверка

Переменные: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_BASE_URL_BACKUP` (из корневого `.env`).

```bash
curl -s localhost:8001/agents | python3 -m json.tool
curl -s -X POST localhost:8001/agents/hyde -H 'Content-Type: application/json' -d '{"input":{"company":"Делимобиль","line":"Закупки"}}'
curl -s localhost:8001/usage        # расход с запуска сервиса, по агентам
uv run pytest agents   # офлайн, без сети
```

## Ограничения

- Бюджет (500 ₽ в сутки) сервис не ограничивает, только считает: `GET /usage`.

## Телеметрия LLM и описания журнала (#29)

Модуль [agents/tracing.py](../agents/tracing.py) задаёт строгую схему события и контекст запуска для всех Python-сервисов. Он копируется в образы backend/news_search/analytics вместе с клиентом. `Agents.run` передаёт внутренние заголовки трассировки, ответный признак неполноты переносится наверх. `TRACE_BACKEND_URL=http://backend:8000` включает доставку событий; для локального запуска задайте доступный адрес backend. Без этой переменной отдельный автономный сервис работает без сохранения журнала; контекст родительского HTTP-запроса всё равно поддерживается.

Учёт вызова, шаг за шагом:

1. HTTP-обёртка наследует запуск или создаёт самостоятельный запуск в backend; публично отдаёт только `X-Run-ID` и `X-Trace-Incomplete`.
2. Каждая JSON-попытка `run` получает пару событий `llm`: агент, разрешённая модель, номер попытки, длительность, статус. Некорректный JSON отмечается `invalid_response`, без текста ответа.
3. Каждый сетевой запрос шлюза, включая повтор и резервный адрес, получает отдельные события `gateway`. Ошибка транспорта и частично полученный usage сохраняются без адреса, ключа и текста исключения. Неизвестные токены/стоимость — null. Для реального расхода суммируйте только завершения `gateway`, а не одновременно `llm` и `gateway`: последние вложены в первые JSON-попытки. При полностью искусственном шлюзе в тестах имеются только `llm`.
4. `GET /usage` считает реальные сетевые попытки и известный usage, включая сбойные. Поля `unknown_usage_calls` и `unknown_cost_calls` показывают, для скольких попыток расход неизвестен; прежние `calls/tokens/cost` сохранены. Счётчик по-прежнему живёт с запуска сервиса; долговременные события хранятся в backend.
5. При недоступности журнала запрос продолжает работу, безопасное событие остаётся в резервном структурированном логе, а журнал помечается неполным. Промпт, ввод пользователя, ответ и скрытые рассуждения не входят в событие.

Новый десятый агент:

| Имя | Модель | Вход | Выход | Кто вызывает |
|---|---|---|---|---|
| `trace_description` | Gemma 4 26B A4B | `events`: до 40 публичных завершённых событий | `descriptions`: `{event_id, phrasing: compact|detail, facts: [counts|queries|sources]}` | backend по явному запросу |

Агент выбирает разрешённое оформление; текст и конкретные факты вставляет backend. Одна JSON-попытка, лимит 2500 токенов, тайм-аут чтения 30 с; сетевой резервный запрос сохраняется. Backend проверяет состав полей, ID, уникальность и полноту фактов, кэширует успешный результат и не описывает события генерации описаний.

`TRACE_AI_ENABLED=false` по умолчанию и проверяется также непосредственно на `POST /agents/trace_description` (503), чтобы прямой вызов не обходил отключение. Включение означает, что оператор подтвердил валюту шлюза и доступный дневной бюджет. Значение `usage.cost` сохраняется в единицах шлюза; в рубли автоматически не переводится. Живой замер Gemma пока не выполнен; ограничение общего бюджета 500 ₽/сутки не реализовано, как и до этой задачи.

## Распознавание обратной связи (#26)

Одиннадцатый агент `feedback_intent` использует разрешённую `google/gemma-4-26b-a4b-it`: вход `{message, context}`, выход `{kind, reason, target_id?, text, line?, region?, url?, refresh, clarification?}`. Виды: `question|extend|perspective|edit|remove|link|proposal|clarify`. `reason` — короткое объяснение распознанного запроса для пользователя, не скрытые рассуждения модели.

Как работает:

1. Backend передаёт сообщение до 8000 символов, ограниченные заголовки/ID и выбранный контекст. Не более 80 виджетов, 160 связей и 40 тыс. символов сериализованного контекста. Прямой HTTP-вызов агента проверяется до модели, иначе 422.
2. Gemma выбирает один сценарий; гипотетические вопросы об удалении остаются question, неоднозначные и составные команды становятся clarify. Нет fallback по ключевым словам, который меняет страницу.
3. `feedback.py` проверяет строгий выход: неизвестный сценарий/поле запрещён, цель только из переданного контекста, URL только из запроса/источника, пользовательская правка дословно скопирована. Некорректный JSON или схема повторяются не более двух JSON-попыток; лимит вывода 1000 токенов, тайм-аут чтения 30 с, сетевой резерв шлюза сохранён.
4. Backend повторно проверяет схему и вызывает только фиксированные обработчики. Вопрос/уточнение не меняют страницу; проверка существования ID не доказывает смысловую правильность классификации.
5. LLM-попытки учитываются обычным механизмом #29; в журнал не попадает сообщение. Клиент Agents также накапливает unknown_cost_calls, чтобы бенчмарк не продолжал расходы при неизвестной стоимости.

Датасет и запуск: [benchmarks/feedback-intents.md](../agents/benchmarks/feedback-intents.md). Цель: macro-F1 >=0,90 и ноль ложных мутаций среди вопросов/неоднозначностей. Живой шлюз пока не проверен: эти показатели, токены, задержка и цена Gemma не объявляются измеренными. Обычная проверка датасета не вызывает LLM. Для живого замера нужны валюта шлюза, доступный дневной бюджет и явный --live; лимит по известному usage проверяется между вызовами и может быть превышен одним вызовом. При ошибке/неизвестном расходе дальнейшие вызовы прекращаются.
