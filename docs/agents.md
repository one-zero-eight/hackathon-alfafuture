# 2. Агенты (Python-сервис `agents`)

Единственное место, где Python-код обращается к LLM организаторов (Go-тегирование в `collector` — отдельное исключение). Код: [agents/app.py](../agents/app.py) (шлюз, агенты и HTTP в одном файле) и [agents/prompts/](../agents/prompts/). Задача сервиса: принять имя агента и данные, собрать запрос, вызвать нужную модель, вернуть проверенный JSON.

## Что делает, шаг за шагом

1. Вызывающий сервис шлёт `POST /agents/{имя}` с `{"input": {...}}`.
2. Сервис проверяет, что агент существует (иначе 404) и что есть все обязательные поля (иначе 422).
3. Шаблон запроса `agents/prompts/<имя>.md` заполняется данными: подставляются только `{поля}` из входа, фигурные скобки примеров JSON остаются как есть.
4. Запрос уходит модели потоковым вызовом (длинные ответы с рассуждениями рвут обычные соединения): сначала основной шлюз, при ошибке резервный. Модель должна быть в списке разрешённых организаторами, иначе вызов отклоняется до сети.
5. Из ответа берётся JSON-объект. Если он пустой, обрезан или в нём нет нужного ключа, запрос повторяется (до 3 раз); если модель потратила весь лимит токенов на рассуждения, лимит следующей попытки увеличивается.
6. Результат приводится к ожидаемому виду (например, `pick` оставляет только известные номера) и возвращается вместе с расходом: вызовы, токены, стоимость.
7. Каждый шаг 3–6 пишется в журнал вызовов (см. ниже), чтобы по нему можно было восстановить, что получила модель, как она рассуждала и что вернула.

## Запросы для обезличенной компании (`queries_anonymised`)

Для компании из данных банка (`U_<цифры>`) вместо названия есть только описание: ОКВЭД, город и регион, число сотрудников, возраст, страны ВЭД, отрасли поставщиков и покупателей. Промпт `queries` требует название в блоке `company_self`, и без него модель писала «компания суд», «компания отзывы» (#37). Поэтому для таких компаний `news_search` вызывает отдельный агент:

1. `news_search` выбирает агента по флагу `anonymised` запроса: `queries_anonymised` вместо `queries` (и в поиске, и в допоиске).
2. Промпт — копия `queries` с тремя отличиями: описание названо описанием, а не названием, и модели сказано взять из него всё (ОКВЭД — ниша и конкуренты, отрасли контрагентов — блоки клиентов и поставщиков, страны ВЭД — курсы, пошлины, логистика, размер и возраст — кредиты и меры поддержки); в блоках конкурентов, клиентов, поставщиков и `government` не меньше трети запросов с регионом или городом; `company_self` всегда пуст, слово «компания» вместо названия и коды ОКВЭД в запросах запрещены.
3. Пустой `company_self` не мешает поиску: этот блок и раньше не участвовал в отборе (`dense_xquad` и `dense_llm` его пропускают, `lexical` выбрасывает найденное только по нему). Поэтому обязательный ключ ответа — `competitors_direct`.

Промпт для компаний с названием не менялся. Замер: [agents/benchmarks/queries-anonymised.md](../agents/benchmarks/queries-anonymised.md).

## Как добавить агента

1. Положите шаблон в `agents/prompts/<имя>.md` с плейсхолдерами `{поле}`.
2. Добавьте запись в `AGENTS` в [app.py](../agents/app.py): модель, обязательные поля, функцию сборки запроса, ключ, который должен быть в ответе, лимит токенов.
3. Допишите вход в тест `test_every_agent_builds_a_prompt_from_minimal_input`.

## Как пользоваться из другого сервиса

```python
from agents.client import Agents

agents = Agents()  # адрес берётся из AGENTS_URL
out = agents.run("hyde", {"company": "Делимобиль", "line": "Закупки"})
print(
    out["headlines"][:3], agents.cost
)  # agents.cost, agents.tokens, agents.calls копятся по экземпляру
```

`agents/client.py` копируется в образы news_search и analytics рядом с их кодом.

## Журнал вызовов

Код: [agents/calllog.py](../agents/calllog.py). Одна строка JSON на событие, в stdout (`docker logs`) и, если задан `AGENTS_LOG_FILE`, дописывается в этот файл. Цель: по журналу восстановить ход мысли модели и увидеть, на каком вызове она начинает нести чушь или зацикливаться на одной теме. Сбой записи журнала вызов не ломает.

Шаги записи:

1. `run()` заводит `call_id` (12 символов) и пишет событие `call`: агент, модель, вход (без картинок, только их число), **полный текст запроса**.
2. Для каждой попытки `chat()` пишет событие `gateway` для каждого обращения к шлюзу: какой шлюз (хост), сколько мс, `finish_reason`, `usage` целиком (включая `reasoning_tokens` и `cost`), **текст рассуждений модели** (`reasoning`) и **сырой ответ** (`content`). Если обращение упало, пишется `ok: false`, ошибка и то, что успело прийти до сбоя.
3. После разбора `run()` пишет событие `attempt`: номер попытки, лимит токенов, исход (`ok` или `retry` с причиной: нет JSON, нет нужного ключа, плохой JSON) и разобранный JSON.
4. Итог: событие `result` с готовым ответом агента или `error`.

Общие поля: `ts` (UTC), `event`, `call_id`, `agent`, `attempt`. События одного вызова связаны через `call_id`; вызовы разных агентов одного запуска различаются по времени и по `input` (компания, роль).

Как читать:

```bash
docker logs alfa-agents-1 2>&1 | grep '^{' > calls.jsonl           # или файл из AGENTS_LOG_FILE
jq -r 'select(.event=="call") | [.ts,.agent,.call_id] | @tsv' calls.jsonl         # какие агенты и в каком порядке
jq -r 'select(.call_id=="<id>") | [.event,.attempt,.outcome,.reason] | @tsv' calls.jsonl   # ход одного вызова
jq -r 'select(.event=="gateway" and .call_id=="<id>") | .reasoning' calls.jsonl   # рассуждения модели
```

Размер: журнал хранит запросы, ответы и рассуждения целиком, в нём тексты новостей и данные компании. Он растёт быстро (запуск профиля даёт сотни КБ), ротации нет; в git его класть не нужно.

## Настройки и проверка

Переменные: `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_BASE_URL_BACKUP` (из корневого `.env`); необязательная `AGENTS_LOG_FILE` — путь файла журнала вызовов.

```bash
curl -s localhost:8001/agents | python3 -m json.tool
curl -s -X POST localhost:8001/agents/hyde -H 'Content-Type: application/json' -d '{"input":{"company":"Делимобиль","line":"Закупки"}}'
curl -s localhost:8001/usage        # расход с запуска сервиса, по агентам
uv run pytest agents   # офлайн, без сети
```

## Ограничения

- Бюджет (500 ₽ в сутки) сервис не ограничивает, только считает: `GET /usage`.
- Имя поля с рассуждениями зависит от шлюза: читаются `reasoning_content` и `reasoning`; проверено на DeepSeek через шлюз организаторов, остальные модели не проверялись. Если у модели рассуждений нет, `reasoning` пуст.
- Журнал не знает, к какому запуску профиля относится вызов: идентификатора запуска в запросе нет.
- Файл журнала в Compose не вынесен на том: без этого он живёт только до пересоздания контейнера (изменение `docker/compose.yaml` — отдельная задача секции docker).

## Распознавание запроса пользователя (#26)

`feedback_intent` определяет вид обращения к странице. Ответ модели проверяется в `agents/feedback.py`: неизвестный вид, цель вне страницы, пустой текст, ссылка не из сообщения или не `http(s)` превращаются в `clarify` с вопросом пользователю. Запроса по ключевым словам нет. Размеченный набор из 80 запросов и расчёт macro-F1: [benchmarks/feedback-intents.md](../agents/benchmarks/feedback-intents.md). Живой замер платный и ждёт подтверждения валюты и бюджета.
