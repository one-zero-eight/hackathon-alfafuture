# Сервис новостей: конфигурация и хранение данных

Реализованы конфигурация, [фиксированный словарь](tag-vocabulary.md), источники,
снимки статей, попытки и результаты тегирования, сохранение бюджетной паузы
в PostgreSQL через `internal/news/store`, общий клиент `llm` для обычных
и потоковых Chat Completions и tool messages, обнаружение записей трёх RSS-лент
и отдельное извлечение текста страниц CBR. Команда `cmd/news` запускает сбор
с записью в БД сразу и по расписанию, независимо для каждого источника.
Один worker автоматически тегирует сохранённые статьи, восстанавливает попытки
после рестарта и соблюдает бюджетную паузу. HTTP API ещё не реализован.

## Загрузка настроек

`config.Load()` вызывается один раз при запуске, до старта goroutine.
Пакет использует [godotenv v1.5.1](https://github.com/joho/godotenv/tree/v1.5.1)
для загрузки `.env` из рабочей директории. Путь можно изменить через `ENV_FILE`;
относительный путь также отсчитывается от рабочей директории.

Уже установленные переменные окружения имеют приоритет, включая пустые значения.
Значения по умолчанию применяются только к отсутствующим переменным: пустое
значение проверяемой настройки считается ошибкой. Пустой `ENV_FILE` выбирает `.env`.
Отсутствие обычного `.env` допустимо, если настройки переданы через окружение.
Явно указанный отсутствующий файл, ошибка чтения или синтаксиса файла возвращают ошибку.
Загрузка дополняет окружение процесса; повторно вызывать её для смены конфигурации не нужно.

| Переменная            | Значение по умолчанию                               | Проверка                                                                         |
|-----------------------|-----------------------------------------------------|----------------------------------------------------------------------------------|
| `DATABASE_URL`        | Обязательная                                        | URL `postgres://` или `postgresql://` с хостом и допустимым портом, без fragment |
| `HTTP_ADDR`           | `127.0.0.1:8080`                                    | `host:port`, порт 1–65535; IPv6-хост в квадратных скобках                        |
| `POLL_INTERVAL`       | `10m`                                               | Положительная длительность Go                                                    |
| `FETCH_TIMEOUT`       | `30s`                                               | Положительная длительность Go                                                    |
| `LLM_TIMEOUT`         | `2m`                                                | Положительная длительность Go для одного LLM-вызова |
| `FETCH_MAX_MB`     | `8`                                           | Положительное целое число мегабайт; размер в байтах должен помещаться в `int64`                           |
| `RBC_FEED_URL`        | `https://rssexport.rbc.ru/rbcnews/news/30/full.rss` | HTTPS, хост `rssexport.rbc.ru`, порт по умолчанию или 443                        |
| `KOMMERSANT_FEED_URL` | `https://www.kommersant.ru/RSS/news.xml`            | HTTPS, хост `www.kommersant.ru`, порт по умолчанию или 443                       |
| `CBR_FEED_URL`        | `https://www.cbr.ru/rss/eventrss`                   | HTTPS, хост `www.cbr.ru`, порт по умолчанию или 443                              |

Для `FETCH_MAX_MB` один мегабайт равен 1 000 000 байт. Например, `8` означает
8 000 000 байт; внутри `Config.FetchMaxBytes` хранится уже пересчитанный размер.
Дробные значения и переполнение при пересчёте отклоняются.

URL источников не должны содержать имя пользователя, пароль или fragment.
Проверка URL БД проверяет форму подключения, но не выполняет запрос к PostgreSQL
и не проверяет параметры конкретного драйвера. Ошибка настроек содержит имя переменной,
но не её значение и не исходное сообщение parser, которое может раскрыть пароль.
Вызывающий код не должен записывать структуру настроек или `DATABASE_URL` в логи.

Общий клиент читает `LLM_API_KEY` и `LLM_MODEL` через `llm.NewFromEnv()` после
`config.Load()`; пакет конфигурации новостей сам не требует API-ключ,
но `cmd/news` проверяет его до подключения к БД и не запускается без ключа.
Безопасное локальное значение `HTTP_ADDR`
позже будет переопределяться внутри контейнера; публикация API останется на localhost.

## Как это работает

1. Пакет выбирает `.env` или файл из `ENV_FILE`.
2. `godotenv` добавляет отсутствующие значения в окружение, сохраняя уже заданные.
3. Пакет читает настройки и применяет значения по умолчанию для отсутствующих переменных.
4. Проверяет URL, адрес прослушивания, интервалы и предел размера ответа; переводит целые мегабайты в байты без переполнения.
5. Возвращает `Config` либо ошибку без значений настроек; вызывающий код прекращает запуск при ошибке.

## Подготовка и проверка

Нужен Go 1.27.3. Из корня репозитория:

```sh
cd backend
cp .env.example .env
go test ./...
go vet ./...
go build ./...
```

В `.env` замените параметры PostgreSQL своими. Пример содержит только демонстрационный
пароль. Файл `.env` исключён из Git, `.env.example` доступен для коммита.
Тесты конфигурации изолируют окружение и используют временные файлы, поэтому реальные настройки,
БД и API-ключи для них не нужны. После первой загрузки зависимости тесты не обращаются в сеть.
Команды запуска сервиса и curl будут добавлены вместе с работающим HTTP API.

## Словарь в PostgreSQL

Пакет `internal/news/store` использует GORM v1.31.2 и PostgreSQL driver v1.6.3.
Проверено на PostgreSQL 18.6. БД принадлежит сервису новостей; другие модули
будут получать справочник через HTTP, без прямой записи в таблицы.

| Таблица | Содержимое | Ограничения |
| --- | --- | --- |
| `vocabulary_versions` | Версия, SHA-256 JSON-представления seed, время создания, JSONB метаданные справочника | Первичный ключ `version` |
| `tags` | Версия, ID, измерение, ID родителя, JSONB со всеми полями тега | Составной первичный ключ `(version, id)`, внешние ключи на версию и родителя той же версии |

В JSONB метаданных находятся источники, критерии отбора, правила назначения,
страновые соответствия, состояния событий и JSON Schema результата; сами теги
хранятся отдельными строками. JSONB тега сохраняет определения, алиасы, ОКВЭД,
ISO/M49 и происхождение родительской связи. Одинаковый ID допустим в разных
версиях. Удаление используемой версии или родителя блокируется внешними ключами.

`store.Open(ctx, databaseURL)` открывает подключение и проверяет его через
`PingContext`. SQL-логирование выключено; ошибки подключения не включают DSN
или пароль. Контекст ограничивает установку подключения, а не весь срок жизни
пула. Вызывающий код закрывает пул через `db.DB()` и `Close()`.

`store.Bootstrap(ctx, db)` инициализирует таблицы словаря, источников, статей,
попыток, назначений тегов, событий и бюджетной паузы,
затем загружает встроенный seed словаря.
Повторный вызов не создаёт дубликатов словаря, не перезаписывает и не удаляет
существующие строки. Источники регистрируются отдельно через `RegisterSources`. Изменение контрольной суммы под уже сохранённым номером версии отклоняется:
для изменения фиксированного справочника требуется новая согласованная версия.
Ручное редактирование словаря в БД не является поддерживаемым способом его обновления.

`store.LoadVocabulary(ctx, db, version)` читает метаданные и теги только из БД,
возвращая `vocabulary.Vocabulary`; теги упорядочены по ID. Для отсутствующей версии
ошибка сохраняет `gorm.ErrRecordNotFound` для проверки через `errors.Is`.

### Как работает инициализация

1. Вызывающий код передаёт проверенный `DATABASE_URL` в `store.Open`.
2. `Bootstrap` загружает встроенный seed и вычисляет его контрольную сумму.
3. В транзакции создаёт начальную схему GORM, если она отсутствует.
4. Добавляет версию, если её ещё нет, и проверяет совпадение контрольной суммы.
5. Вставляет отсутствующие теги; БД проверяет уникальность, версию и родительские связи.
6. Фиксирует транзакцию целиком; при ошибке изменения этой транзакции откатываются.
7. Последующее чтение использует строки PostgreSQL, а не JSON из сборки.

Это начальная схема для MVP. Перед изменением структуры на постоянных данных
нужно перейти к версионированным миграциям вместо дальнейшего изменения схемы
через AutoMigrate. `cmd/news` вызывает `Bootstrap` при запуске.

### Проверка с настоящей БД

Без `TEST_DATABASE_URL` обычный `go test ./...` явно пропускает PostgreSQL-тесты.
Для их выполнения нужен Docker и отдельная тестовая БД. Из корня репозитория:

```sh
docker run --detach --rm --name alfafuture-vocabulary-test \
  --cpus=1 --memory=512m --tmpfs /var/lib/postgresql \
  -e POSTGRES_USER=news_test -e POSTGRES_PASSWORD=news_test -e POSTGRES_DB=news_test \
  -p 127.0.0.1:55432:5432 postgres:18.6-alpine
docker exec alfafuture-vocabulary-test pg_isready -U news_test -d news_test
cd backend
TEST_DATABASE_URL='postgres://news_test:news_test@127.0.0.1:55432/news_test?sslmode=disable' \
  go test -count=1 ./...
go vet ./...
go build ./...
docker stop alfafuture-vocabulary-test
```

Если `pg_isready` ещё не сообщает о готовности, повторите проверку перед запуском
тестов. Пароль выше демонстрационный и относится только к временному контейнеру.
Контейнер не использует постоянные volumes; его тестовые данные удаляются при остановке.
Пользователь БД должен иметь право создавать схемы. Каждый PostgreSQL-тест создаёт
случайную собственную схему, задаёт её в `search_path` для всех подключений,
проверяет `current_schema()` до миграции и удаляет только эту схему при завершении. Окружение приложения и его `DATABASE_URL` тесты
хранилища не читают.

Проверяются все 525 тегов и метаданные после повторного подключения, идемпотентность,
уникальность, версии и родители, защита используемых записей от удаления, конфликт
контрольной суммы, атомарный откат неудачной загрузки и отсутствие credentials в
ошибке разбора подключения. Также проверяются сохранность источников и статей,
дедупликация и одновременные вставки, описанные ниже. Проверка HTTP и постоянного
volume будет выполнена вместе с их реализацией.

## Источники и снимки статей

`Source` и `Article` — модели внутреннего хранилища, а не HTTP DTO.

| Таблица | Содержимое | Ограничения |
| --- | --- | --- |
| `sources` | ID, название, URL RSS, первый cutoff и время регистрации, последний опрос, последний успешный опрос и ошибка | Первичный ключ `id`; регистрация обновляет только название и URL |
| `articles` | ID, источник, GUID и исходный URL, заголовок, время публикации при наличии, время сбора, текст, происхождение текста, ошибка извлечения и статус обработки | Уникальность `(source_id, dedup_key)`, внешний ключ на источник, проверки статуса и происхождения текста |

`RegisterSources(ctx, db, sources, now)` принимает настройки выбранных источников.
При первой регистрации каждого источника сохраняет `CollectionSince = now - 24h`
и время создания. При повторной регистрации меняет только `Name` и `FeedURL`,
сохраняя cutoff и историю опросов. Все настройки проверяются до первой записи,
затем записываются одной SQL-операцией. У источника должны быть ID, название
и HTTPS URL без credentials или fragment. Выбор трёх утверждённых источников
и ограничения их хостов задаются конфигурацией и клиентами коллектора.

`ListSources(ctx, db)` читает источники по ID. `RecordSourcePoll(ctx, db, sourceID,
at, pollErr)` сохраняет время последней попытки и её ошибку. Успех очищает
последнюю ошибку и обновляет время успеха; ошибка не стирает предыдущий успех
и не меняет другие источники. Коллектор должен передавать диагностические
ошибки без credentials. Неизвестный источник возвращает `gorm.ErrRecordNotFound`.

### Идентичность и первый снимок

`InsertArticle(ctx, db, article)` возвращает сохранённую статью, признак новой
вставки и ошибку. Новый ID назначает PostgreSQL, статус новой статьи — `pending`.
GUID используется как непрозрачная строка; только при пустом GUID применяется
точный исходный URL. Идентификаторы GUID и URL имеют разные префиксы, чтобы
GUID, совпавший с URL другой записи, не создавал ложного совпадения.

В индексе хранится SHA-256 такой строки идентичности; исходные GUID и URL
сохраняются отдельно. Благодаря этому длинный GUID не попадает в B-tree целиком.
Уникальность включает источник: одинаковые новости разных издателей не сливаются.
Разные непустые GUID не объединяются по одному URL. Нормализация URL и
семантическое объединение публикаций не выполняются.

Конфликт уникальности возвращает уже сохранённую статью с признаком `false`,
не заменяя её URL, заголовок, время публикации/сбора или текст. Ограничение БД
защищает от дубликатов и при одновременных вставках. `FindArticle(ctx, db,
sourceID, sourceItemID, articleURL)` проверяет ту же идентичность до
загрузки страницы или вызова LLM. `LoadArticle(ctx, db, id)` читает снимок по ID.
Отсутствующие записи возвращают `gorm.ErrRecordNotFound`.

Время сбора обязательно. Время публикации может отсутствовать; оно не заменяется
временем сбора. Заголовок может быть пустым, но не подставляется вместо текста.
Правило допуска реализует коллектор: датированные записи до сохранённого cutoff
пропускаются, записи на границе и новее принимаются. По решению пользователя
от 2026-10-23 записи без пригодной даты принимаются с `PublishedAt = null`;
cutoff к ним не применяется. При этом их возраст установить нельзя.

Для непустого текста обязательно одно из значений `TextProvenance`:

- `rss_description` — описание или анонс из RSS;
- `rss_full_text` — полный текст из расширения издателя в RSS;
- `article_page` — текст, извлечённый со страницы публикации.

Без текста provenance должна быть пустой. Ошибка извлечения может сохраняться
в `TextError`, а статья — оставаться `pending` в ожидании текста; такая запись
не объявляется готовой к LLM-тегированию. Непустой текст одновременно с ошибкой
извлечения отклоняется. SQL также проверяет допустимые provenance и статусы
`pending`, `processing`, `completed`, `failed`.

### Сохранение результата извлечения текста

`RecordArticleText(ctx, db, articleID, text, provenance, extractionErr)` возвращает
сохранённую статью. Успех требует непустого текста, известного provenance и
отсутствия ошибки; неудача — пустых текста/provenance и непустой диагностики.
Вызывающий код передаёт безопасную ошибку без credentials, например из `FetchText`.
ID должен быть положительным; неизвестная статья возвращает `gorm.ErrRecordNotFound`.

Одна SQL-операция обновляет только `Text`, `TextProvenance` и `TextError`, причём
только у статьи с пустым текстом и статусом `pending`. Неудача сохраняет диагностику;
успешный повтор заполняет текст и очищает предыдущую ошибку. Уже заполненная
статья или статья в другом статусе возвращается без изменений. Это сохраняет
первый успешный снимок и при одновременных результатах извлечения: поздний успех
или ошибка не заменяет сохранённый текст. Метаданные и статус тегирования не меняются.

`ListArticlesAwaitingText(ctx, db, sourceID)` читает статьи выбранного источника
с пустым текстом и статусом `pending`, по возрастанию ID. В выборку входят
сохранённые ошибки, даже если публикация уже исчезла из RSS. Пустой ID источника
отклоняется, неизвестный источник даёт пустую выборку. Эта операция только читает:
не назначает повторы, не блокирует очередь и не меняет cutoff.

### Как сохраняется результат и восстанавливается незавершённое извлечение

1. Вызывающий код сохраняет метаданные через `InsertArticle`; без текста статья остаётся `pending`.
2. После `FetchText` передаёт текст/provenance либо ошибку в `RecordArticleText`.
3. PostgreSQL заполняет ещё пустой снимок или сохраняет ошибку, оставляя метаданные неизменными.
4. После нового подключения `ListArticlesAwaitingText` возвращает незавершённые статьи из БД.
5. Явный успешный повтор через `RecordArticleText` очищает ошибку; последующие результаты сохраняют первый текст.

### Как используется хранилище при сборе

1. При запуске вызывающий код выполняет `Bootstrap` и регистрирует настройки источников.
2. Коллектор читает сохранённый cutoff каждого источника, не вычисляя новый после рестарта.
3. Для записи RSS сначала вызывает `FindArticle`, чтобы проверить дубликат до загрузки страницы.
4. После получения нормализованных данных вызывает `InsertArticle`; БД сохраняет первый снимок либо возвращает существующий.
5. Коллектор отдельно записывает результат опроса каждого источника.
6. Последующее чтение получает исходную ссылку, времена и provenance из PostgreSQL.

Операции хранилища подключены к сбору по расписанию, включая допуск по дате
и повторы извлечения. Очередь тегирования и смена статусов worker подключены;
HTTP DTO добавляются вместе с HTTP-модулем.
Эти проверки используют ту же команду `TEST_DATABASE_URL=... go test -count=1 ./...`,
что приведена выше; реальные RSS/HTML и LLM не вызываются. Проверки извлечения
проходят на настоящем PostgreSQL: ошибка сохраняется после переподключения,
успешный повтор очищает её, первый текст выдерживает одновременные записи,
выборка исключает другой источник, готовый текст и статьи вне `pending`.

## Попытки и результаты тегирования

| Таблица | Содержимое | Ограничения |
| --- | --- | --- |
| `tagging_attempts` | Статья, номер попытки, версия словаря и prompt, модель, точный текст и JSON тела запроса, ответ, времена, статус, ошибка, nullable token usage | Уникальность `(article_id, number)`, внешние ключи на статью и версию; проверки статуса, времени завершения и неотрицательных token counts |
| `tag_assignments` | Попытка, версия и ID тега, дословный фрагмент текста | Первичный ключ `(attempt_id, tag_id)`, внешние ключи на попытку той же версии и тег словаря |
| `event_instances` | Попытка, ID назначенного тега события, nullable статус, собственный фрагмент текста | Внешние ключи на попытку и назначение, проверка допустимого статуса |
| `budget_pauses` | Одна запись с nullable временем окончания паузы | Единственный допустимый ID — `1` |

`StartAttempt(ctx, db, input)` блокирует строку статьи, проверяет `pending`
и совпадение `InputText` с сохранённым снимком. Пустой текст к тегированию
не допускается. Хранилище назначает следующий номер попытки, сохраняет запрос
и переводит статью в `processing` одной транзакцией. Неизвестная статья или
версия словаря не создаёт частичную попытку. Из нескольких одновременных
вызовов для одной статьи проходит один; остальные получают `ErrArticleNotPending`.
`Request` хранит исходную строку JSON-объекта, включая форматирование, без
HTTP-заголовков и API-ключа. Формирование тела запроса и проверка модели принадлежат
вызывающему коду и общему LLM-клиенту.

`FinishAttempt(ctx, db, id, completion)` завершает только `processing`-попытку.
Непустой указатель `Result` означает успех; пустые списки тегов и событий
являются допустимым результатом. Сохраняются ответ и token usage, назначения,
отдельные события и статус статьи `completed`. Отсутствующая статистика токенов
остаётся `NULL`; известный ноль сохраняется нулём, стоимость в рублях не вычисляется.
Повторное завершение возвращает `ErrAttemptNotProcessing` без перезаписи истории.

При `Result == nil` обязательны ошибка и явно выбранный `FailureStatus`:
`pending` для будущего повтора или `failed` для окончательной ошибки. Сама попытка
получает `failed` в обоих случаях. Выбор повторяемых ошибок, задержки и предел
числа вызовов здесь не реализуются — это ответственность worker. Некорректный
модельный ответ нужно завершать как ошибку, сохраняя его исходный текст.

Перед успешной записью `ValidateTaggingResult` проверяет уже согласованный
[контракт результата](tag-vocabulary.md): известные уникальные ID, непустые
дословные цитаты из точного входного текста, связь событий с назначенными
тегами измерения `event`, наличие экземпляра для каждого тега события и отсутствие
полных дубликатов экземпляров. Статус отдельного события: `observed`,
`announced_planned`, `forecast` либо `NULL`; несколько событий одного типа
с разными статусами или цитатами сохраняются отдельно. Географические предки
и членство в экономических группах автоматически не назначаются.

Это проверка типизированного результата, а не JSON-декодер и не проверка
семантической точности модели. Для внешнего ответа вызывающий код сначала
применяет `tagging.Decode`: он проверяет обязательные JSON-поля, лишние ключи
и затем вызывает тот же валидатор. Ошибка проверки или любой последующей
SQL-операции откатывает завершение целиком, включая статус статьи.

`LoadAttempts(ctx, db, articleID)` читает все попытки по номеру, включая ошибки
и незавершённые запросы; назначения упорядочены по ID тега, события — по ID записи.
Пустая история возвращает пустой результат, неверный неположительный ID — ошибку.
`LoadAttempt(ctx, db, attemptID)` читает одну попытку с исходным запросом,
текстом и версией, без загрузки назначений и событий. Неположительный ID
отклоняется, неизвестный возвращает `gorm.ErrRecordNotFound`.

`SetBudgetPause(ctx, db, until)` сохраняет срок приостановки провайдера в UTC;
`nil` очищает паузу. `LoadBudgetPause` возвращает сохранённое время либо `nil`,
если пауза не задана. Хранилище не вычисляет 03:00 Москвы, не проверяет истечение
срока и не вводит дневной лимит: эти решения выполняет worker по ответу провайдера.

### Как сохраняется результат

1. Вызывающий код формирует запрос из фиксированного словаря и снимка статьи.
2. `StartAttempt` сохраняет входные данные и фиксирует `processing` до вызова LLM.
3. Вызывающий код отправляет сохранённый запрос, разбирает ответ и передаёт результат либо ошибку в `FinishAttempt`.
4. Хранилище проверяет результат и одной транзакцией сохраняет ответ, usage, цитаты, события и итоговый статус статьи.
5. При сбое транзакции попытка остаётся незавершённой; частично записанные результаты не доступны.
6. После переподключения worker читает историю и паузу из PostgreSQL и восстанавливает незавершённые попытки в общем пределе повторов.

Проверка выполняется приведённой выше командой `TEST_DATABASE_URL=... go test -count=1 ./...`.
Тесты проверяют смешанные observed/forecast/NULL события, пустой результат,
ошибки и следующую попытку, защиту завершённой истории, отсутствующий usage и
известный ноль, восемь одновременных захватов, внешние ключи и SQL-проверки,
полный откат при конфликте на последней записи, сохранение и очистку паузы
после нового подключения. Это проверки хранилища без обращения к реальному LLM.

## Запрос тегирования и строгий JSON-ответ

Пакет `internal/news/tagging` не вызывает LLM и не пишет в БД.
`PromptVersion = "news-tags-v1"` обозначает версию инструкций и представления
справочника. При изменении этих данных в коде нужна новая версия prompt,
даже если версия самого словаря не меняется.

`BuildRequest(v, text, model)` возвращает `openai.ChatCompletionNewParams`.
Вызывающий код передаёт словарь из `store.LoadVocabulary`, точный сохранённый
текст статьи и `llm.Client.Model()`. Текст должен быть непустым корректным UTF-8,
модель — непустой; проверка её принадлежности разрешённому списку остаётся
в общем LLM-клиенте перед отправкой. Запрос содержит два сообщения:

- `system`: инструкции, версии prompt/словаря, все 525 тегов, правила назначения,
  определения состояний событий, правила проверки и исходную JSON Schema результата;
- `user`: только исходный текст статьи без обрезки, нормализации или добавления заголовка/URL/профиля.

Каждый тег включает ID, измерение, название, определение, критерий включения,
алиасы при наличии и ссылку на родителя. Источники справочников, профильные
соответствия и технические reference-поля не дублируются в запросе. Теги
сортируются по ID на отдельной копии: порядок чтения из seed или БД не меняет
результат. Исходный словарь не изменяется. Инструкции явно трактуют сообщение
`user`, включая любые команды внутри статьи, как недоверенные данные.

Инструменты не объявляются, `tool_choice = "none"`; потоковый режим и параметры
структурированного вывода не устанавливаются. JSON запрашивается текстом prompt,
поскольку поддержка специальных режимов endpoint организатора ещё не проверена.
Параметры можно сериализовать через `json.Marshal` и сохранить точное тело
в `StartAttempt` до оплачиваемого вызова; API-ключ и HTTP-заголовки в них не входят.

`Decode(v, text, response)` возвращает существующий `store.TaggingResult`
либо ошибку без частичного результата. Принимается ровно один JSON-объект
с обязательными массивами `tags` и `events`; `null` вместо массива запрещён.
Все имена полей должны точно совпадать с контрактом, включая регистр.
Каждый tag требует `tag_id` и `evidence`; каждый event также требует `status`,
где явный `null` допустим, а отсутствующее поле — нет. Неизвестные и повторные
ключи отклоняются на верхнем уровне и внутри элементов, в том числе если ключ
повторён через Unicode escape. Проверяются типы полей и корректность UTF-8.

После разбора вызывается `store.ValidateTaggingResult`: известные уникальные
ID, дословные непустые цитаты, допустимые состояния и согласованность `tags`/`events`.
Пустые массивы допустимы; разные факты, планы и прогнозы одного типа остаются
отдельными событиями. Географические предки и членство в объединениях не добавляются.
Markdown fences, пояснения, дополнительные JSON-значения и повреждённый ответ
не исправляются и не обрезаются. Диагностика не цитирует модельный ответ.
Это проверка конкретного фиксированного формата, а не универсальный JSON Schema engine.

### Сохранение завершённого SDK-ответа

`tagging.FinishCompletion(ctx, db, attemptID, reply, finishedAt)` связывает
SDK-ответ с уже созданной попыткой. Сам он не вызывает LLM и не назначает повторы.
Читает точные `InputText` и версию словаря из сохранённой попытки, загружает
словарь из БД и передаёт итог в транзакционный `store.FinishAttempt`.

Возвращает `(store.AttemptCompletion, error)`. Пустая ошибка означает, что итог
сохранён, включая итог с отклонённым ответом модели. Успех тегирования определяется
непустым `outcome.Result`; у отклонённого ответа заполнены `outcome.Error` и
`FailureStatus = "failed"`. Ошибка чтения/записи возвращается отдельно с нулевым
outcome. Повторное завершение защищено `ErrAttemptNotProcessing`, ранее записанный
ответ не заменяется. Время должно быть не раньше начала попытки; ошибка оставляет
попытку незавершённой, не записывая частичные результаты.

Принимается ровно один выбор с `finish_reason = "stop"`, ролью `assistant`,
без refusal, tool calls или legacy function call. Содержимое проходит `Decode`.
Пустой SDK-ответ, отсутствие исходного `RawJSON`, обрезанный ответ (`length`),
неподходящее число выборов и невалидный результат становятся сохранёнными ошибками,
а статья — `failed`, без исправляющего платного запроса и без назначений.
Это обработка уже полученного ответа; сетевые ошибки и прерванные незавершённые
вызовы будут отдельно обрабатываться worker.

`Response` сохраняет `reply.RawJSON()` целиком, включая дополнительные поля
провайдера; это не только строка `message.content`. Счётчики usage извлекаются
по SDK-метаданным наличия: отсутствующий/null остаётся `NULL`, известный ноль — `0`.
Отрицательный счётчик или неверный тип usage делает ответ ошибочным; непригодные
счётчики остаются неизвестными, остальные корректные сохраняются. Исходный ответ
при этом остаётся в трассе. Его содержимое не попадает в диагностическую строку.
API-ключи и заголовки запроса этот путь не записывает.

Проверки на настоящем PostgreSQL используют настройку тестовой БД выше:

```sh
TEST_DATABASE_URL='postgres://news_test:news_test@127.0.0.1:55432/news_test?sslmode=disable' go test -count=1 ./internal/news/tagging ./internal/news/store
```

SDK-ответы синтетические, без HTTP/LLM: проверяются смешанные события, null/zero/partial
usage, неверные типы и отрицательные значения, truncated/refusal/tool replies,
сохранение успеха и ошибки после переподключения, защита готовой истории,
отсутствующие ID и сохранность незавершённого запроса при ошибке времени.
2026-10-23: полный набор PostgreSQL-тестов, vet и build прошли; реальные LLM-запросы
не выполнялись. Эта операция подключена к worker вместе с timeout/backoff,
восстановлением прерванных запросов и бюджетной паузой, описанными ниже.

Политика worker уточнена 2026-10-23: не более двух повторов после
первого вызова, то есть максимум три попытки. Используются предложенные задержки
10 и 30 секунд и timeout 2 минуты; повтор после рестарта входит в тот же предел,
а не начинает новый счётчик. Невалидный завершённый ответ не запускает repair-повторы.
Эта политика применяется при исполнении запросов.

### Как подготовить и проверить результат

1. Получить сохранённый словарь и непустой снимок статьи.
2. Вызвать `BuildRequest`, сохранив версии, точный текст и сериализованные параметры.
3. Worker сохраняет попытку до вызова `llm.Chat`.
4. Для полученного SDK-ответа вызвать `FinishCompletion`: он применит `Decode` к тексту без изменения цитат.
5. Операция передаст результат либо ошибку вместе с raw response и доступным usage в `FinishAttempt`.
6. Ошибочный ответ не становится тегами; готовый текст ответа не запускает автоматический repair-запрос.

Из `backend/`, без БД, ключа API и сети:

```sh
go test -count=1 -v ./internal/news/tagging
go test ./...
go vet ./...
go build ./...
```

Fixtures проверяют полное сохранение классификационных полей справочника,
детерминированный запрос, разделение ролей и точный текст с попыткой подменить
инструкции, все четыре состояния событий, отдельные противоположные прогнозы,
пустой результат, неверные типы/ключи/null, дубликаты, лишний JSON и нелитеральные цитаты.
2026-10-23: для v1 системное сообщение составляет 329 407 байт UTF-8 и 221 072
кодовые точки Unicode, без текста статьи. Это не число токенов и не оценка цены.
Большой prompt требует проверки контекстного окна и фактического usage выбранной
модели перед массовой обработкой; все 525 тегов передаются в каждом запросе.

Семантическая точность модели, устойчивость к prompt injection и совместимость
запроса с реальным endpoint пока не проверены. Наличие дословной цитаты само
по себе не доказывает правильность выбранного тега или состояния. Платные запросы
в fixture-проверке не выполнялись; worker, повторы и восстановление бюджета
подключены к `cmd/news` и проверены отдельно на синтетических ответах.

## Общий Go-клиент LLM

Пакет `github.com/one-zero-eight/hackathon-alfafuture/backend/llm` доступен другим
Go-модулям без импорта `internal/news`. Он использует Chat Completions
[официального Go SDK v3.85.1](https://developers.openai.com/api/reference/go).
API пакета не является отдельным HTTP-сервисом.

| Вызов | Назначение |
| --- | --- |
| `llm.New(apiKey, model) (*llm.Client, error)` | Проверяет ключ и модель; пустая модель выбирает `llm.DefaultModel` |
| `llm.NewFromEnv() (*llm.Client, error)` | Читает `LLM_API_KEY` и `LLM_MODEL` из уже подготовленного окружения |
| `client.Model() string` | Возвращает настроенную модель по умолчанию для построения и сохранения запроса |
| `client.Chat(ctx, params) (*openai.ChatCompletion, error)` | Выполняет один обычный запрос с `openai.ChatCompletionNewParams` |
| `client.ChatStream(ctx, params) (*ssestream.Stream[openai.ChatCompletionChunk], error)` | Открывает один SSE-запрос; дальнейшее чтение и закрытие принадлежат вызывающему коду |

`LLM_API_KEY` обязателен и должен быть непустым ASCII-токеном без пробелов
и управляющих символов. `LLM_MODEL` по умолчанию —
`deepseek/deepseek-v4.1-flash`; только отсутствующая переменная использует default,
явно пустая или неизвестная модель отклоняется. Конструктор не выполняет запросов.
`NewFromEnv` сам не загружает `.env`: сервис сначала подготавливает окружение
своим конфигуратором. В `backend/.env.example` оставлено пустое место для ключа;
реальный ключ хранится только локально, в исключённом из Git файле или окружении.

Разрешены только точные ID:

- `google/gemma-4-26b-a4b-it`;
- `z-ai/glm-5.3-flash`;
- `qwen/qwen3.6-35b-a3b`;
- `deepseek/deepseek-v4.1-flash`;
- `qwen/qwen3-vl-30b-a3b-instruct`;
- `moonshotai/kimi-k2.6`.

`params.Model` может выбрать другую модель из этого списка для одного запроса.
При пустом поле применяется настроенная модель; исходная структура вызывающего
кода не изменяется. Запрос должен содержать хотя бы одно сообщение. Произвольная
замена всего тела через SDK `param.Override`/`param.SetJSON`, а также подмена
`model` или `stream` через `SetExtraFields` запрещены, чтобы проверка модели
не расходилась с отправленным запросом. Остальные обычные параметры SDK
передаются без собственного набора DTO.

Endpoint фиксирован: `https://changellenge.up.railway.app/v1/`;
обычный запрос — `POST /v1/chat/completions`. Другие провайдеры и резервные модели
не выбираются. Используется SDK `NewChatCompletionService`, который сам не
читает ambient `OPENAI_*` настройки: сторонний `OPENAI_BASE_URL`, ключи,
organization/project и custom headers не меняют этот клиент. HTTP redirects
и автоматические retries отключены. Пакет не пишет запросы, ключи или ответы в логи.

Клиент сохраняет типы SDK: сообщения system/user/assistant/tool, определения
функций, tool calls и результаты инструментов. Инструменты исполняет вызывающий
сервис. Например, после проверки непустого `response.Choices` он может добавить
`response.Choices[0].Message.ToParam()` в историю, затем добавить
`openai.ToolMessage(result, callID)` и самостоятельно сделать следующий запрос.
Сам пакет не запускает агентный цикл и не выполняет дополнительные платные вызовы.

### Пример использования

После загрузки окружения вызывающий код может использовать такую функцию:

```go
import (
    "context"

    "github.com/openai/openai-go/v3"
    "github.com/one-zero-eight/hackathon-alfafuture/backend/llm"
)

func ask(ctx context.Context) (*openai.ChatCompletion, error) {
    client, err := llm.NewFromEnv()
    if err != nil {
        return nil, err
    }
    return client.Chat(ctx, openai.ChatCompletionNewParams{
        Model: client.Model(),
        Messages: []openai.ChatCompletionMessageParamUnion{
            openai.UserMessage("Какие события описаны в предоставленном тексте?"),
        },
    })
}
```

Один клиент можно переиспользовать между вызовами. Deadline и отмену задаёт
вызывающий код через `context.WithTimeout`/`context.WithCancel`; функция выше
получает уже подготовленный контекст. Ошибки возвращаются без собственного
преобразования: `errors.Is(err, context.Canceled)` сохраняет смысл, а
`errors.As(err, &apiErr)` с `var apiErr *openai.Error` даёт HTTP status, code,
message и исходный ответ для выбора дальнейшего действия.
В JSON-ошибке текст бюджетного ограничения доступен через `apiErr.Message`;
у не-JSON ошибки исходное тело остаётся в `apiErr.Response.Body`.
Запрос в ошибке, raw diagnostics и response body могут содержать секреты или
исходный текст: их не следует целиком помещать в общие логи.
Пауза до 03:00 Москвы и политика повторов реализованы worker, а не общим клиентом.

### Usage и точный ответ

Результат — исходный `openai.ChatCompletion`; `response.RawJSON()` сохраняет
полученный JSON. Отсутствующий usage нельзя определять по нулевым числам:

- `response.JSON.Usage.Valid()` проверяет наличие ненулевого объекта usage;
- `response.Usage.JSON.PromptTokens.Valid()` проверяет отдельный счётчик входа;
- аналогично проверяются `CompletionTokens` и `TotalTokens`.

Только после проверки соответствующего поля используется его числовое значение.
Отсутствующий объект, JSON `null`, частичная статистика и явно известный ноль
остаются различимыми. Цены моделей организаторы не указали; рублёвая стоимость
из числа токенов не выводится.

### Как проходит запрос

1. Вызывающий сервис загружает окружение и создаёт клиент с ключом организатора.
2. Передаёт контекст, историю сообщений и при необходимости определения tools.
3. Клиент выбирает настроенную модель либо проверяет явно переданный допустимый ID.
4. SDK отправляет один запрос на фиксированный endpoint без redirects и повторов.
5. Клиент возвращает исходный ответ, tool calls, метаданные наличия usage либо ошибку.
6. Вызывающий сервис сохраняет результат и сам решает, выполнять ли инструмент или повторять запрос.

Проверка из `backend/`: `go test -count=1 ./llm`; все Go-пакеты —
`go test ./...`, затем `go vet ./...` и `go build ./...`.
HTTP fixtures выполняются в памяти через тестовый transport, без sockets, ключа
организатора, Docker и реального endpoint. Они проверяют маршрут и Authorization,
все шесть моделей, окружение, историю и tool round trip, варианты usage, ошибки,
отсутствие повторов, запрет redirects и отмену контекста.
Остальные PostgreSQL-тесты по-прежнему требуют `TEST_DATABASE_URL`, как описано выше.

Работа именно с endpoint организаторов, включая поддержку tools, streaming
и usage, пока **не проверена на реальном сервисе**;
успех протокольных fixtures не доказывает поддержку этих возможностей провайдером.

### Потоковые ответы

`ChatStream` принимает те же параметры и применяет ту же проверку модели,
что и `Chat`. SDK добавляет `stream: true`. Ошибка проверки, подключения или HTTP
возвращается сразу как второй результат вызова; в этом случае stream равен `nil`.
После открытия потока вызывающий код использует `Next()`, `Current()`, `Err()`
и `Close()` из `github.com/openai/openai-go/v3/packages/ssestream`.
Чтение выполняется по мере вызовов `Next`, отдельной фоновой очереди в пакете нет.

Типы и поля [streaming-протокола](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)
сохраняются: `Choices[].Index`, `Delta.Content`, `Delta.ToolCalls[].Index`, ID,
части имени и аргументов функции, `FinishReason` и `RawJSON()` каждого chunk.
Аргументы tool call могут быть неполным JSON до получения остальных частей.
Разные инструменты собираются по их индексам внутри соответствующего choice;
инструмент исполняется вызывающим кодом только после завершения и проверки аргументов.
При необходимости можно использовать существующий `openai.ChatCompletionAccumulator`
вместо собственного сборщика. У его вычисленных tool calls нужно читать поля
`Function.Name`/`Function.Arguments` напрямую: `AsFunction()` декодирует raw JSON,
который accumulator для вычисленных объектов не создаёт.

Статистику запрашивает вызывающий код через SDK
`StreamOptions: openai.ChatCompletionStreamOptionsParam{IncludeUsage: openai.Bool(true)}`.
Клиент не добавляет этот параметр автоматически и не повторяет запрос, если
провайдер его не поддерживает. Chunk с usage может иметь пустой `Choices`;
его нужно обработать независимо от текста и tool calls. Наличие объекта и каждого
счётчика проверяется через `chunk.JSON.Usage.Valid()` и метаданные `chunk.Usage.JSON`,
как у обычного ответа. Сохраните usage из полученного chunk отдельно: сумма полей
accumulator не заменяет проверку доступности статистики. При потере финального
chunk usage остаётся неизвестным, включая случаи уже полученного текста.

Пример чтения текста после создания `client`, контекста `ctx` и SDK-параметров `params`:

```go
stream, err := client.ChatStream(ctx, params)
if err != nil {
    return err
}
defer func() { _ = stream.Close() }()

finishReason := ""
for stream.Next() {
    chunk := stream.Current()
    for _, choice := range chunk.Choices {
        if choice.Index == 0 {
            fmt.Print(choice.Delta.Content)
            if choice.FinishReason != "" {
                finishReason = choice.FinishReason
            }
        }
    }
    // Inspect chunk.JSON.Usage even when chunk.Choices is empty.
}
if err := stream.Err(); err != nil {
    return err
}
if finishReason != "stop" {
    return errors.New("text response did not finish normally")
}
```

Пример использует стандартные пакеты `fmt` и `errors`, читает текст первого
choice и считает успешным только `stop`. Для tools вызывающий код отдельно
обрабатывает `tool_calls`; `length` означает ограниченный по длине ответ.
Обрыв соединения с ошибкой, невалидный JSON, SSE error и отмена контекста
становятся `stream.Err()` после `Next() == false`. Структурированные SSE-ошибки
SDK доступны как `*ssestream.StreamError` с исходными данными события; их текст
может включать ответ провайдера, поэтому правила безопасного логирования остаются
теми же. Ни один из этих случаев не запускает повторный платный запрос.

Ограничение SDK: чистый EOF может дать `Err() == nil` без `[DONE]`. Поэтому
одно завершение итерации не доказывает полноту ответа: нужен `FinishReason`
для каждого используемого choice. Если финальный usage не получен, стоимость
не считается нулевой. Автоматической проверки полноты или восстановления потока
в этом пакете нет. `Close()` обязателен при досрочном выходе; его можно безопасно
повторить. При обычном завершении или ошибке SDK закрывает body сам.

### Как читается поток

1. Вызывающий код передаёт сообщения, контекст и при необходимости tools/запрос usage.
2. `ChatStream` проверяет параметры и открывает один запрос на endpoint организатора.
3. `Next` читает очередной SSE chunk, а `Current` возвращает исходные поля SDK.
4. Вызывающий код собирает текст и tool calls, отдельно сохраняя доступный usage.
5. После окончания проверяет `Err` и причины завершения; частичный ответ не объявляется полным.
6. При досрочном выходе закрывает поток; ошибки и обрывы автоматически не повторяются.

Проверка: из `backend/` выполнить `go test -count=1 ./llm`. Дополнительные fixtures
проверяют перемежающиеся фрагменты двух tool calls, часть имени и аргументов,
совместимость с accumulator, usage-only chunk, отсутствующие/null/частичные/нулевые
счётчики, чистый EOF без завершения, HTTP/SSE/JSON/transport ошибки, истёкший
deadline, отмену во время чтения, досрочное закрытие и освобождение body один раз.
Подмена модели/stream через SDK overrides проверяется для обоих способов вызова.

## Обнаружение RSS-записей

Внутренний пакет `internal/news/feed` разделяет обнаружение записей RSS
и извлечение текста: `Discover` не загружает страницы статей и не обращается к БД
или LLM. Пакет использует [gofeed v1.5.0](https://github.com/mmcdole/gofeed/releases/tag/v1.5.0)
для метаданных и `golang.org/x/net/html` v0.60.0 для текстового представления.
HTTP DTO и OpenAPI будут подключены вместе с HTTP-сервисом.

`feed.New(sourceID, feedURL, timeout, maxBytes)` создаёт клиент одного источника.
Вызывающий код передаёт существующие `Config.FetchTimeout` и
`Config.FetchMaxBytes`; пользовательский лимит по-прежнему задаётся целыми
мегабайтами в `FETCH_MAX_MB`. При создании сеть не вызывается. Допустимые ID
и хосты фиксированы:

| ID | Хост RSS и разрешённых redirects | Хост ссылок на статьи | Текст при discovery |
| --- | --- | --- | --- |
| `rbc` | `rssexport.rbc.ru` | `www.rbc.ru` | Непустой publisher full text, иначе description |
| `kommersant` | `www.kommersant.ru` | `www.kommersant.ru` | Только description |
| `cbr` | `www.cbr.ru` | `www.cbr.ru` | Отсутствует до отдельного извлечения страницы |

`client.Discover(ctx) (feed.Discovery, error)` возвращает `Entries` и
`RejectedItems` — число элементов с неподходящими ссылками. Каждый `Entry`
содержит `SourceID`, непрозрачный `SourceItemID` из GUID, `URL`, `Title`,
nullable `PublishedAt`, `Text`, `TextProvenance` и `TextError`.
Отсутствующий GUID остаётся пустым для последующего exact-URL fallback в БД.
URL сохраняется в виде, полученном от parser, без дополнительной канонизации
и перестановки query-параметров. Дубликаты намеренно остаются в discovery:
проверка сохранённой идентичности должна предшествовать будущей загрузке страниц.

Время публикации берётся из публикационных полей RSS, сохраняется в UTC;
при отсутствии или неразбираемой дате остаётся `nil`. Время обновления,
время сбора или текущие часы не подставляются. Начальный cutoff и допуск
записей по дате относятся к планировщику, а не этому пакету.

У РБК выбирается точное XML-имя `{https://www.rbc.ru}full-text`, независимо
от имени namespace prefix. Для этого выполняется небольшой дополнительный
разбор `encoding/xml`: универсальная модель gofeed хранит prefix расширения,
но не его URI. Элемент с похожим prefix и другим URI не считается полным текстом.
Если full text отсутствует или пуст после нормализации, используется description.
Другие расширения и связанные новости не добавляются к тексту.

HTML преобразуется в текст: script/style/template/noscript не включаются,
блочные элементы разделяются пробелами, entities декодируются, последовательности
пробельных символов сворачиваются. Inline-элементы не разрывают слово.
Полученный текст становится будущим сохраняемым снимком и точным входом LLM.
`rss_full_text` и `rss_description` обозначают происхождение, а не оценку качества.
Без пригодного RSS-текста сохраняется пустой `Text`, пустой provenance и
диагностика `TextError`; заголовок не подменяет статью. Для CBR пустой текст
не является ошибкой discovery: HTML-извлечение вызывается отдельно через `FetchText`.

### Сетевые ограничения и ошибки

RSS URL и redirects допускают только HTTPS, исходный хост источника, порт
по умолчанию либо 443, без credentials и fragment. Цепочка ограничена пятью
HTTP-запросами, включая исходный; путь может измениться на том же хосте.
Это позволяет использовать redirect «Коммерсанта» с `/RSS/` на `/rss/`.
Ссылки статей допускают только хост соответствующего издателя, HTTP/HTTPS
со стандартными портами и без credentials. Некорректная ссылка отклоняет
один элемент с увеличением счётчика, а не весь корректный остаток ленты.

Принимается HTTP 200. Timeout ограничивает HTTP-запрос и чтение body;
context позволяет отмену. Проверяется заявленный Content-Length, затем
фактический объём читается с пределом `maxBytes + 1` для обнаружения превышения,
включая ответы без Content-Length. При автоматической распаковке HTTP transport
проверяется уже читаемый распакованный поток. Нулевые, отрицательные timeout/лимит
и лимит, переполняющий проверку дополнительного байта, отклоняются при создании.
Body закрывается при успехе и ошибках. Отменённый до вызова context не запускает запрос.

Ошибки содержат безопасное описание стадии или HTTP status, без исходного URL,
ответа и транспортного текста, которые могут раскрыть query или credentials.
`errors.Is` различает отмену и истечение timeout. Ошибка запроса, превышение
лимита или неразбираемая лента возвращают ошибку всего discovery данного источника.
Автоматических повторов нет. Управление независимыми опросами и сохранение
их статуса выполняются коллектором отдельно от адаптера RSS.

### Как проходит обнаружение

1. Вызывающий код создаёт клиент с URL и существующими пределами загрузки.
2. Клиент получает одну ленту с проверкой redirects, статуса и размера ответа.
3. gofeed разбирает RSS, а для РБК отдельно читается namespace full-text.
4. Для каждой допустимой ссылки сохраняются идентичность, заголовок, дата и доступный RSS-текст с provenance.
5. Вызывающий код получает записи и число отклонённых элементов.
6. Коллектор применяет cutoff, проверяет БД и лишь затем загружает нужную страницу CBR.

### Проверка

Из `backend/`, без БД и ключа LLM:

```sh
go test -count=1 ./internal/news/feed
go test ./...
go vet ./...
go build ./...
```

Обычные тесты используют синтетические RSS/HTML и HTTP transport в памяти,
не открывают sockets и не обращаются к издателям. Проверяют namespace и fallback,
provenance, отсутствующие даты/GUID/текст, повторяющиеся записи, ошибочные ссылки,
malformed/unsupported feed, нормализацию HTML, redirects, точный и превышенный
размер, закрытие body, безопасные ошибки, отмену и timeout.

Отдельная проверка требует доступа к трём публичным сайтам и выполняет по одному
discovery на источник с лимитом 8 MB и timeout 30s, без платных запросов:

```sh
LIVE_RSS_TEST=1 go test -run '^TestLiveRSS$' -count=1 -v ./internal/news/feed
```

Проверка 2026-10-22: реализованный клиент получил 30 записей РБК, все с full text,
и 100 записей CBR без подстановки заголовков в текст. Live-запрос «Коммерсанта»
истёк по timeout; контрольные Go/Python-запросы также завершались TLS EOF,
поэтому текущая доступность этого endpoint не подтверждена. Сохранённый при
успешном чтении публичный ответ дополнительно проверен самим адаптером:
623 записи «Коммерсанта», все с description, без отклонённых ссылок.
Для РБК и CBR сохранённые публичные ответы также прошли адаптер.
Текст реальных новостей в тестовые fixtures и репозиторий не включён.

Ограничение: namespace-разбор РБК использует строгий `encoding/xml` и может
отклонить повреждённый XML, который gofeed сумел бы частично восстановить.
Извлечение страниц CBR выполняется отдельным `FetchText`, описанным ниже.
Повторы, cutoff, проверка сохранённых дубликатов и запись по расписанию
выполняются пакетом `internal/news/collect`, а не RSS-адаптером.

## Текст статей CBR

`client.FetchText(ctx, entry) (feed.Entry, error)` — вторая стадия после
`Discover`. Коллектор сначала применяет cutoff и проверяет сохранённую
идентичность, затем вызывает её только при необходимости получения текста.
Общий контракт для трёх источников:

- `SourceID` записи должен совпадать с источником клиента; несовпадение — ошибка вызова.
- Непустой `Text` возвращается без изменений и без нового HTTP-запроса.
- Пустой текст РБК/«Коммерсанта» остаётся ошибкой отсутствующего RSS-текста; их страницы не загружаются.
- Для CBR с пустым текстом загружается страница по исходному URL записи.

Запрос CBR допускает только HTTPS URL на `www.cbr.ru`, порт по умолчанию
либо 443, без credentials и fragment. Используется тот же HTTP reader, что
для RSS: context, timeout, проверка статуса и размера, не более пяти запросов
в цепочке redirects на том же хосте, закрытие body и ошибки без сырых URL/ответов.
Не происходит автоматического исправления HTTP-ссылок в HTTPS или обхода TLS.

HTML разбирается уже установленным `x/net/html`. В первом `main` с точным
`id="content"` выбираются `div` с отдельным class token `lead-text` или
`landing-text` в порядке документа. В [проверенном примере CBR](https://www.cbr.ru/press/event/?id=32925)
первый абзац находится в `lead-text`, остальные — в `landing-text`; извлечение
одного только landing-text потеряло бы начало статьи. Избранные контейнеры
нормализуются существующей функцией текста RSS: скрытые script/style/template/noscript
исключаются, блоки разделяются пробелами, entities и whitespace нормализуются.
Вложенный выбранный контейнер не добавляется повторно. Пустой один из контейнеров
допустим, если другой содержит текст.

Заголовок страницы, дата, navigation и footer вне выбранных контейнеров
не подставляются в статью. Ссылки и PDF не загружаются. Если основной контейнер
не найден либо подходящих lead/body с пригодным текстом нет, возвращается ошибка,
пустые `Text`/`TextProvenance` и безопасный `TextError`. Страница с одним h1
не считается успешно извлечённой новостью.

При успехе заполняются `Text`, `TextProvenance = "article_page"` и очищается
предыдущий `TextError`. GUID, исходный URL, RSS-заголовок и время публикации
сохраняются даже после допустимого redirect. Входная структура вызывающего кода
не изменяется. При сетевой ошибке или ошибке layout извлечённая запись и
возвращённая ошибка позволяют коллектору сохранить диагностику и
повторить загрузку явно; сам пакет не выполняет retry и не пишет в БД.
Проверки source mismatch относятся к ошибке вызова, а не результату извлечения.

### Как извлекается текст

1. Вызывающий код получает метаданные через `Discover` и проверяет БД до загрузки страницы.
2. Передаёт нужную запись в `FetchText`; уже заполненный текст возвращается сразу.
3. Для CBR проверяется URL и загружается ограниченный HTTP-ответ.
4. В HTML находятся lead/body внутри `main#content`; общий normalizer превращает их в текст.
5. Возвращается запись с provenance либо диагностикой, сохраняя исходные метаданные.
6. Коллектор сохраняет результат; неудачная загрузка повторяется на следующем опросе источника.

Из `backend/`, без БД, ключа LLM и сети:

## Сбор по расписанию и запуск

`collect.New(ctx, db, cfg)` создаёт клиентов трёх настроенных источников,
регистрирует их в уже инициализированной БД и читает сохранённые границы сбора.
Все настройки клиентов проверяются до регистрации. Повторная регистрация
не сдвигает cutoff и не стирает историю. Пул принадлежит вызывающему коду.

`collector.Run(ctx)` вызывается один раз. Для каждого источника запускается
собственная goroutine: первый опрос сразу, последующие — по `POLL_INTERVAL`
(по умолчанию 10 минут). Опросы одного источника не перекрываются. Если опрос
дольше интервала, ticks объединяются стандартным ticker; второй параллельный
опрос не запускается. Отмена контекста прерывает запросы и ожидает все goroutine.

Датированные статьи до cutoff отбрасываются до записи и загрузки страницы.
Статьи без даты сохраняются с null, без подстановки текущего времени.
Для остальных сначала проверяется идентичность через `FindArticle`, затем
`InsertArticle` сохраняет метаданные и имеющийся RSS-текст. Повторные записи
с готовым текстом не требуют страницы и не меняют снимок. Если у сохранённой
статьи РБК/«Коммерсанта» текста ещё нет, появившийся в новой ленте RSS-текст
может заполнить его через `RecordArticleText`, сохранив первые метаданные.

После discovery CBR читает из БД все свои `pending` статьи без текста.
Каждая строка загружается один раз за опрос, даже если RSS повторил запись.
Метаданные сохраняются до HTTP-запроса страницы: незавершённую работу можно
найти после рестарта. Ошибка извлечения сохраняется в статье, следующая попытка
происходит при следующем опросе. Очередь читается и при ошибке самого CBR RSS,
поэтому исчезновение записи из ленты не лишает её повтора. Страницы загружаются
последовательно; большой backlog может продлить опрос CBR за пределы интервала,
но не блокирует другие источники. Лимит числа повторов для этих загрузок не введён.

Ошибка RSS или неполученный текст делает результат опроса ошибочным, но не
останавливает другие источники и не отменяет уже сохранённые статьи.
`RecordSourcePoll` обновляет время попытки и безопасную диагностику; предыдущий
успех сохраняется. Следующий полностью успешный опрос очищает ошибку.
При отмене незавершённый опрос не записывается как сбой издателя.
Постоянная ошибка самой БД видна в логах; записать её в недоступную БД нельзя.

Команда выводит JSON-логи без DSN, API-ключей, текста статей или сырых ответов:
источник, результат, счётчики discovered/rejected/inserted/duplicates/too_old/undated,
text_failures и recovered. Последний считает успешное заполнение пустого текста,
включая первое извлечение страницы. Undated считает элементы текущей ленты,
в том числе повторные, а не общее число статей без даты в БД.

### Как работает полный цикл сбора

1. `cmd/news` читает настройки, открывает PostgreSQL, выполняет `Bootstrap` и создаёт коллектор.
2. Для каждого источника независимо получает RSS сразу после старта.
3. Пропускает только известные даты до сохранённой границы; отсутствующие оставляет null.
4. Проверяет идентичность и сохраняет новую статью либо использует первый снимок.
5. Для CBR извлекает текст уникальных незавершённых статей из БД и сохраняет успех или ошибку.
6. Сохраняет результат опроса, ждёт следующего tick и повторяет; Ctrl+C/SIGTERM отменяет работу и закрывает пул.

## Постоянный worker тегирования

`tagging.NewWorker(ctx, db, client, timeout)` загружает фиксированную версию
словаря из PostgreSQL. В production передаётся общий `llm.Client`; callback-интерфейс
`Model`/`Chat` позволяет тестировать границу без платных запросов. `Run(ctx)`
обрабатывает очередь одним потоком независимо от горутин сбора.

Перед восстановлением worker занимает session advisory lock для текущей БД/схемы.
Второй процесс не может восстановить ещё работающую попытку или запустить второй
worker. Соединение с lock закреплено до остановки; потеря соединения прекращает
worker, lock освобождается при завершении. Соединение, которое не удалось явно
разблокировать, не возвращается в пул. Это требует отдельного соединения сверх
рабочих SQL-запросов; текущий пул не ограничен одним соединением.

Очередь — `pending` статьи с непустым текстом, по ID. Пустой текст, `completed`
и `failed` не выбираются. Пустая очередь проверяется раз в секунду. Worker
обслуживает старшую статью вместе с её повторами: ожидание 10/30 секунд пока
задерживает новые статьи. Отдельного планировщика приоритетов в MVP нет.

До вызова API `BuildRequest` сериализуется и сохраняется через `StartAttempt`
вместе с точным текстом, версиями и моделью. В этот момент статья уже `processing`.
Тест HTTP transport сверяет сохранённую строку с фактически отправленным SDK body.
Далее работает `LLM_TIMEOUT` (по умолчанию 2 минуты); скрытые повторы SDK отключены.

| Исход вызова | Действие |
| --- | --- |
| Полный корректный ответ | `FinishCompletion` атомарно сохраняет raw response, доступный usage, назначения/события и `completed` |
| Невалидный, обрезанный, отказной или tool-ответ | `failed`, без repair-запроса |
| Connection error, timeout, EOF, HTTP 408/429/5xx | Не более двух повторов с задержками 10 и 30 секунд; третья неудачная попытка даёт `failed` |
| Остальные HTTP-ошибки и неповторяемые ошибки клиента | `failed` без повторов |
| `Budget has been exceeded` в JSON или plain-text HTTP error | Атомарно сохранить попытку и паузу всего тегирования до следующего 03:00 Москвы |
| Потеря БД при сохранении результата | Прекратить worker и сервис без немедленного replay; незавершённая попытка останется для восстановления |

Если SDK не предоставил raw body при ошибке разбора ответа, `Response` остаётся
пустым и usage неизвестен; вымышленный ответ или нулевая стоимость не подставляются.

Каждый сохранённый вызов, включая бюджетный отказ и прерванный запрос, входит
в общий предел трёх попыток на статью. Рестарт не сбрасывает этот счётчик.
Задержка вычисляется по последнему `FinishedAt`, а не хранится только в памяти:
новый процесс дожидается оставшегося времени. При восстановлении `processing`
попытка закрывается с ошибкой неизвестного исхода/usage; статья возвращается
в `pending`, если осталось меньше трёх попыток, иначе становится `failed`.
Прерванный запрос мог быть оплачен, поэтому повтор может потребовать второй оплаты.

Бюджет проверяется перед каждой новой попыткой. `FinishBudgetAttempt` одной
транзакцией сохраняет попытку, статус статьи и `BudgetPause`. На третьей попытке
статья становится `failed`, но общая пауза всё равно сохраняется. До 03:00 запросы
не отправляются; после срока пауза очищается и очередь продолжается. Ответ ровно
в 03:00 или позже задаёт паузу до следующего дня. Используется `Europe/Moscow`,
tzdata включена в бинарник. Дополнительного дневного лимита модуля нет, цены
моделей неизвестны; provider usage не преобразуется в неподтверждённые рубли.
Сбор RSS и запись новых статей продолжаются во время паузы.

При Ctrl+C/SIGTERM текущий LLM-вызов отменяется. Уже полученный ответ или
подтверждённая HTTP-ошибка сохраняется с отдельным контекстом до 5 секунд;
отменённый вызов отмечается как прерванный с неизвестным usage. Если сохранить
нельзя либо процесс аварийно завершился, следующий worker восстановит `processing`.
После остановки worker команда отменяет и дожидается коллектора, затем закрывает БД.
Логи содержат ID статьи, номер попытки, итог, безопасную ошибку и nullable counters;
raw response, текст запроса, ключи и заголовки в логи не включаются.

### Как проходит тегирование статьи

1. Получить lock и закрыть незавершённые попытки, сохранив общий счётчик.
2. Прочитать бюджетную паузу; при необходимости дождаться её окончания.
3. Выбрать первую `pending` статью с текстом и выдержать оставшуюся задержку повтора.
4. Сохранить точный запрос/версии до одного ограниченного по времени вызова `Chat`.
5. Сохранить проверенный ответ или безопасную ошибку с имеющимся usage.
6. Перейти к следующей статье, задержке, бюджетной паузе либо штатной остановке.
