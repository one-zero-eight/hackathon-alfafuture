# Backend (Python, FastAPI)

Оркеструет остальные сервисы, хранит профили пользователей и готовые страницы, отвечает фронту. Код: [backend/](../backend/).

## Что делает, шаг за шагом

1. В стартовом меню пользователь выбирает компанию из списка банка (`GET /api/companies`) и описывает роль. Фронт шлёт `POST /api/profile`.
2. Бэкенд превращает запись в ключ: `sha1(компания | сфера | регион | метод поиска)`, 12 символов. Опечатки и синонимы одной сферы («закупкки», «снабжение») дают один ключ. Другой метод поиска даёт другой ключ.
3. Профиль кладётся в таблицу `profiles` со статусом `queued`. Если такая страница уже готова и ей меньше `PROFILE_TTL_HOURS` (24 часа), она отдаётся сразу и бесплатно.
4. Фоновый поток бэкенда берёт `queued` профиль и ставит ему `running`.
5. Компания: если введён id вида `U_123` (обезличенные данные банка), по CSV собираются описание для поиска и карточка для аналитики ([companies.py](../backend/companies.py)). Иначе в поиск уходит введённый текст.
6. Строка роли разбирается ([focus.py](../backend/focus.py)): должность выбирает правила решений (по умолчанию финансовый директор), отрасль или тема передаётся как «сфера».
7. `POST news_search/search` с методом из `NEWS_SEARCH_METHOD` возвращает топ-30 новостей и связки. В запрос уходит `locality` (0–1) из карточки компании: 1 минус процентиль выручки среди всех компаний данных банка (без выручки — по штату: менее 15 — 0,8, 16–100 — 0,5, 101–250 — 0,3, более 251 — 0,1), при внешнеэкономической деятельности вдвое меньше; для компании, введённой по названию, — 0,1. По нему поиск добавляет крупным компаниям федеральные новости ([news-search.md](news-search.md)).
8. `POST analytics/page` строит из них новости, аналитику и решения.
9. Бэкенд добавляет ко всем id виджетов и связей префикс ключа (так id уникальны между страницами), сохраняет страницу в `profiles.page` и ставит статус `ready`. Любая ошибка попадает в `profiles.error`, статус `failed`.
10. Пока идёт работа, воркер пишет в `profiles` этап (`search` → `rank` → `analysis`) и числа новостей. Фронт раз в 1,5 секунды спрашивает `GET /api/profile/{key}`, при `ready` просит `GET /api/page?profile={key}`.

Без профиля `GET /api/page` отдаёт демо-страницу про Газпром ([backend/demo/seed.json](../backend/demo/seed.json)); её правки из чата живут в памяти до перезапуска.

## Выбор метода поиска новостей

Переменная окружения `NEWS_SEARCH_METHOD` (в [.env](../.env.example) и compose): `lexical`, `dense_llm` или `dense_xquad` (по умолчанию). Описание методов: [news-search.md](news-search.md). Неизвестное значение останавливает бэкенд при старте.

## Обратная связь и чат (#26)

Все обращения пользователя (вопрос, правка, вставка ссылки, удаление, «Спросить ИИ») идут через один вход `POST /api/chat`. Открытие чата (`message: null`) отдаётся сразу из сохранённой страницы. Сообщение превращается в операцию очереди:

1. Бэкенд проверяет версию страницы (`page_version`), и кладёт операцию в `feedback_operations` (PostgreSQL). Ответ `202` с `operation_id`. Повтор с тем же `request_id` возвращает первую операцию и не запускает вторую: платные вызовы не дублируются.
2. Фоновый поток берёт операцию и проверяет, что версия страницы всё ещё та. Иначе операция получает статус `conflict`.
3. Агент `feedback_intent` (Gemma, [agents](agents.md)) определяет вид запроса. Цели (`target_id`) и ссылка проверяются по странице и тексту сообщения. Неясный запрос становится `clarify` с уточняющим вопросом; запроса по ключевым словам нет.
4. Дальше цепочка по виду запроса:

| Вид | Что делает бэкенд |
|---|---|
| `question` | `POST analytics/reply` по виджету, связи или всей странице; в ответе источники выбранной части |
| `extend` | `POST news_search/refine` (`topic`) без уже показанных и удалённых новостей → `POST analytics/page` по новым → новые цепочки добавляются к странице |
| `perspective` | `refine` (`perspective`) с новым регионом/направлением → `analytics/page` → сгенерированные блоки заменяются, блоки с текстом пользователя остаются; новая перспектива запоминается |
| `link` | страница по ссылке скачивается безопасно ([article_fetch.py](../backend/article_fetch.py)) → `refine` (`link`) → `analytics/page` по статье и найденному |
| `remove` | виджет и его **исключительные** сгенерированные потомки (все родители удалены) убираются; общие и пользовательские блоки остаются; статья и адрес запоминаются как исключённые |
| `edit` | текст блока становится пользовательским (`source: human`), оригинальный источник сохраняется. Если на новости или выводе построены другие блоки, вызывается `POST analytics/revise` (контракт ниже) |
| `proposal` | `POST analytics/revise` по тексту предложения: с какими выводами согласуется, матрица рисков |

5. Допоиск (`/refine`) всегда идёт методом `dense_xquad`, каким бы методом посчитан профиль.
6. Новая страница публикуется в одной транзакции: проверка версии под блокировкой, запись ревизии прежней страницы (хранятся последние 20), новая версия `+1`. Операция получает результат с `patch`, который фронт применяет как обычно.

Состояние пользователя хранится в `profiles.feedback_state`: источники (`sources`) и из каких статей написан каждый новостной виджет (`widget_sources`), исключённые статьи/адреса, действующая перспектива (`effective`), виджеты с текстом пользователя (`manual_ids`). Происхождение виджета — `tags.source`: `human` (текст или ссылка пользователя), `ai` (генерация), `alfa` (материал банка); ссылки на источники остаются у новостных виджетов.

Прочее: завершённые операции и их входные данные хранятся 7 дней; операция, прерванная перезапуском, получает `failed`, платные вызовы автоматически не повторяются.

## Ограничения

- Одна фоновая задача за раз: профили считаются по очереди.
- Одна операция обратной связи за раз (отдельный поток); публикация проверяет версию страницы под блокировкой, конфликт — статус `conflict`.
- Пересчёт профиля после истечения кэша (`PROFILE_TTL_HOURS`) начинает с чистой страницы: правки старой версии не переносятся (shortcut: перенос исключений и правок вместе с `force=true` не сделан). Прежняя версия остаётся в ревизиях.
- `POST analytics/revise` (#28) в аналитике ещё не реализован: пока его нет (404), `edit` блока с зависимыми блоками и `proposal` завершаются `blocked`/`analytics_unavailable`, страница не меняется.
- Если файлов `df_Uid_*.csv` нет, профиль с `company_id` получает статус `failed` и понятную причину.

# Контракт между фронтом и бэкендом

Все пути начинаются с `/api`, формат — JSON, кодировка UTF-8. В разработке Vite проксирует `/api` на `http://127.0.0.1:8000` (адрес задаётся в [frontend/vite.config.ts](../frontend/vite.config.ts)).

## Как работает страница

1. Фронт запрашивает `GET /api/page` и сразу рисует три блока: только заголовки виджетов и стрелки между ними.
2. Всё остальное подгружается по действиям пользователя и кэшируется:
   - клик по виджету (раскрытие) → `GET /api/widgets/{id}`;
   - «Матрица рисков» → `GET /api/widgets/{id}/risks`;
   - клик по стрелке → `GET /api/links/{id}`;
   - кнопка «Спросить» внизу виджета или в окне стрелки → `POST /api/chat`.
3. Ответ чата может содержать `patch`. Фронт применяет его к странице: добавляет, меняет или удаляет виджеты и стрелки.
4. У страницы есть `version`. Каждый патч увеличивает её на 1. Если `base_version` патча не совпал с версией у фронта, фронт перезагружает `/page` и сбрасывает кэш.

## Схемы

```
Column   = "news" | "analytics" | "decisions"
Widget   = { id, column: Column, title, url?: string, tags?: Tags }   // url — ссылка на оригинал (кнопка «источник» в раскрытом виджете)
Link     = { id, from: <id виджета>, to: <id виджета> }               // стрелка идёт слева направо: news→analytics→decisions
Tags     = { confidence?, source?, industry?, urgency?, kind? }           // см. раздел «Теги»
Company  = { name, okved, role, date }
```

## Теги

Теги лежат в скелете виджета (`tags` в `GET /api/page` и в патчах), поэтому видны и на свёрнутом виджете. Все поля необязательны. Значения в API — английские, подписи на русском подставляет фронт.

| Поле | Значения | Смысл | Где ставится |
|---|---|---|---|
| `confidence` | `reliable` (достоверно), `probable` (вероятно), `possible` (возможно) | степень уверенности в выводе | аналитика, решения |
| `source` | `ai` (ИИ), `alfa` (Альфа), `human` (человек) | чей это анализ | новости (только `alfa` для материалов банка), аналитика, решения |
| `industry` | произвольная строка («Китай», «Автомобилестроение») | отрасль или тема новости | новости |
| `urgency` | `urgent` (срочно), `medium_term` (среднесрочно), `not_urgent` (не срочно) | срочность действия | решения |
| `kind` | `fact` (факт), `conclusion` (вывод модели), `hypothesis` (гипотеза) | чем является текст карточки | новость — факт; аналитика и решение — вывод модели, а если вторая модель его не подтвердила — гипотеза |

Правило для `source: "human"`: сервер ставит его виджету, который создан или изменён на основе слов пользователя из чата (просьба что-то добавить, изменить, переделать). Вывод, сделанный ИИ без таких слов, остаётся `ai`, а на основе материала банка — `alfa`. При изменении тегов сервер присылает их в патче целиком (`update_widget`, `fields.tags`).

## Профиль пользователя

Пользователь выбирает в стартовом меню компанию и вводит роль текстом (или сферу анализа). Сервер готовит под них страницу в фоне: поиск по корпусу новостей, отбор и ИИ-анализ. Первый раз это занимает минуты, повторы того же запроса в течение суток берутся из кэша.

`POST /api/profile` с телом `{"company": "…", "role": "…", "region": "…", "company_id": "U_123"}`:

- `role` обязательно; нужно либо `company`, либо `company_id` (вид `U_` и цифры; такой id можно ввести и в поле `company`);
- `region` необязательно; для `company_id` регион берётся из данных банка;
- все поля до 200 символов, иначе 422.

Ответ: `{"key": "…", "status": "queued|running|ready|failed", "error": "", "cached": false}`. Ключ `key` зависит от компании, сферы, региона и метода поиска. `cached: true` значит, что страница уже была в базе и отдана сразу (статус `ready`, анализ не запускается; тот же кэш на `PROFILE_TTL_HOURS`). `GET /api/profile/{key}` возвращает `{key, status, error, stage, found, selected}` (404, если профиля нет); фронт опрашивает его раз в 1,5 секунды, пока статус `queued` или `running`. `stage` — `search` (формирование запроса и поиск в БД), `rank` (`found` — сколько новостей найдено, идёт отбор), `analysis` (`selected` — сколько новостей отобрано для анализа); `found` и `selected` равны `null`, пока неизвестны. Поиск идёт одним вызовом `news_search`, поэтому `rank` бэкенд отмечает после его ответа, а не во время ранжирования. При `failed` в `error` причина; повторный `POST` ставит профиль в очередь заново.

`GET /api/companies?q=&offset=0&limit=50` (`limit` до 200) возвращает `{"total": n, "items": [{"id": "U_67", "okved_name": "…"}]}` из `df_Uid_data_hack.csv` в порядке файла; `q` — подстрока id или названия ОКВЭД без учёта регистра. 503, если CSV недоступен.

Когда статус `ready`, фронт запрашивает `GET /api/page?profile={key}` (404, если страницы ещё нет). Без параметра `profile` возвращается демо-страница. Ключ профиля фронт хранит в `localStorage`. Если у компании нет карточки банка, `company.okved` равен `"не указан"`. Id виджетов и связей страницы профиля начинаются с `{key}_`.

Ссылка `url` виджета аналитики может вести на страницу PDF Альфа-Банка: `/api/papers/<файл>.pdf#page=N`.

## POST /api/ad-tip

Совет Альфа-Бизнеса, который фронт показывает под таймлайном, пока строится страница. Тело: `{"company": "U_123" или название, "role": "…"}` (оба поля обязательны, роль до 500 символов). Как работает:

1. Для `U_…` берётся карточка банка (`CompanyBook.profile`): описание компании без id, `CL_TYPE` и отметки продуктов. Для компании по названию карточки нет.
2. `ad_offer` ([companies.py](../backend/companies.py)) по `CL_TYPE` и продуктам выбирает цель: `PROSPECT` — стать клиентом (открыть расчётный счёт); `CLOSE_CLIENT` — вернуться в Альфа-Бизнес; `CLIENT` без расчётного счёта — перейти в Альфа-Бизнес; `CLIENT` со счётом — до двух услуг, которых у него нет (кредиты, лизинг, депозиты, зарплатный проект, банковские гарантии, факторинг), а если есть все, то «новые возможности»; статус неизвестен — узнать об Альфа-Бизнесе.
3. Агент `ad_tip` пишет совет в 1–2 предложения по сфере компании и роли с этим предложением в конце.
4. Ответ `{"text": "…", "cl_type": "PROSPECT|CLIENT|CLOSE_CLIENT|null"}` запоминается по паре (компания, роль) в памяти процесса (после перезапуска пропадает).

Ошибки: 422 пустые поля, 404 неизвестный `U_…`, 502 агент недоступен (фронт скрывает виджет).

```bash
curl -s -X POST localhost:3000/api/ad-tip -H 'Content-Type: application/json' -d '{"company":"U_123","role":"Финансовый директор"}'
```

## GET /api/widgets/{id}

Раскрытое содержимое виджета. 404, если виджета нет.

```json
{
  "id": "a1",
  "text": "База 2025 — 38,8 млрд м³ …",
```

## GET /api/widgets/{id}/risks

Матрица рисков решения. 404, если виджет не решение или его нет.

```json
{
  "id": "d2",
  "steps": ["Определить долю долга под плавающую ставку."],
  "bank_offer": "процентные свопы … в Альфа-Бизнес",
  "risks": [{"name": "Ставка не снизится", "probability": 3, "impact": 3, "mitigation": "Ступенчатая фиксация."}]
}
```

`probability` и `impact` — целые 1–4 (клетка матрицы 4×4). `bank_offer` — нативное предложение банка, может быть `null`.

Шкала одна и та же для вероятности и для влияния, уровни не складываются:

| | Вероятность | Влияние |
|---|---|---|
| 1 | почти не случится | заметно едва |
| 2 | может случиться | бьёт по одной операции |
| 3 | скорее случится | бьёт по денежному потоку или отчётности |
| 4 | этого исхода стоит ждать | ставит под вопрос само решение |

## POST /api/chat

Единый вход ИИ: вопрос, дополнение темы, новая перспектива, правка, вставка ссылки, удаление. Работает из любой точки интерфейса.

Запрос:

```json
{
  "context": {"type": "widget", "id": "n1"},
  "session_id": null,
  "message": "Удали эту новость, она неактуальна",
  "page_version": 1,
  "request_id": "b0c1…"
}
```

- `context.type` — `widget`, `link` или `page` (для `page` `id` — ключ профиля: запрос ко всей странице, например вставка ссылки).
- `message: null` — открыть чат: сервер сразу вернёт вступительное сообщение и подсказки (`200`, `patch: null`).
- `message` — 1…4000 символов. Ответ `202` с `{session_id, operation_id, status: "queued"}`; результат читается по `GET /api/feedback/{operation_id}`.
- `request_id` — необязательный, до 64 символов. Повтор с тем же значением и тем же сообщением возвращает первую операцию (`200`); то же значение с другим сообщением — `409`.
- `session_id` — `null` в первом запросе, дальше фронт присылает то, что вернул сервер.
- `page_version` — версия страницы у фронта.

Ошибки: 404 — нет такого виджета, связи или страницы; 409 — `page_version` не совпала (фронт перезагрузит страницу); 422 — пустое или слишком длинное сообщение.

Демо-страница (без профиля) отвечает сразу, по-старому: заготовленные правки «добавь…»/«измени…» в памяти.

## GET /api/feedback/{operation_id}

```json
{
  "operation_id": "…", "status": "completed",
  "result": {
    "session_id": "…", "version": 2,
    "scenario": {"kind": "remove", "reason": "Пользователь просит убрать новость"},
    "reply": {"text": "Изменения сохранены.", "basis": [], "followups": []},
    "patch": {"base_version": 1, "version": 2, "ops": []},
    "changes": [{"op": "removed", "id": "n1", "title": "…"}],
    "sources": [{"ref": "article:1", "title": "…", "url": "https://…", "origin": "search"}]
  }
}
```

- `status`: `queued`, `running` (опрашивать), `completed`, `needs_clarification` (в `reply.text` вопрос пользователю), `blocked`, `failed`, `conflict`. Для `blocked`/`failed`/`conflict` в `result.error` есть `code` и `message`, страница не изменена.
- `scenario.kind`: `question`, `extend`, `perspective`, `edit`, `remove`, `link`, `proposal`, `clarify` — что распознано и почему.
- `changes` — что добавлено, заменено или удалено (`op`: `added`, `updated`, `removed`); `patch` — как применить это на фронте (`null`, если страница не менялась).
- `sources` — источники ответа или новых блоков; `origin`: `search` (поиск), `human` (текст или ссылка пользователя), `alfa`.
- Коды ошибок: `sources_refresh_required` (старая страница без сохранённых источников), `no_news`, `analytics_unavailable`, `analytics_bad_response`, `article_fetch_failed`, `page_conflict`, `processing_failed`, `interrupted`.

## POST analytics/revise (контракт для #28)

Бэкенд вызывает его для `proposal` и для `edit` блока, на котором построены другие блоки. Запрос:

```json
{"kind": "edit | proposal", "profile": {}, "role": "CFO", "sphere": "", "text": "формулировка или предложение пользователя",
 "target": {"id": "…", "column": "analytics", "title": "…", "details": {"text": "уже новый текст пользователя"}},
 "page": {"widgets": [{"id": "", "column": "", "title": "", "text": "", "source": "ai|human|alfa"}], "links": [{"from": "", "to": ""}]},
 "sources": [{"ref": "article:1", "title": "", "url": "", "origin": "search|human"}]}
```

`profile`, `role`, `sphere` — как в `/page`; `target` — `null` для `proposal`. Ответ:

```json
{"reply": {"text": "что и почему изменилось", "basis": ["короткие опоры"]},
 "widgets": [{"id": "локальный id", "column": "decisions", "title": "…", "tags": {}, "details": {"text": ""}, "risks": {"steps": [], "bank_offer": null, "risks": []}}],
 "links": [{"id": "", "from": "id с страницы или локальный id", "to": "…", "text": "почему связаны"}],
 "updates": [{"id": "id с страницы", "fields": {"title": "", "details": {}, "tags": {}, "risks": {}}}],
 "removed": ["id с страницы"]}
```

Бэкенд сам выдаёт новым виджетам и связям id страницы, связи на неизвестные id отбрасывает, в `updates` принимает только `title`, `details`, `tags`, `risks`, `chat`, `url`. Матрица рисков — в формате существующего `risks` виджета (формат итоговой матрицы согласуется отдельно). Ответ 404 бэкенд читает как «эндпоинта ещё нет».

## POST /api/profile/{key}/undo

Тело `{"page_version": 3}`. Возвращает страницу к состоянию до последнего изменения как **новую** версию: `{patch, changes, version}`. Повтор идёт дальше назад (хранятся последние 20 ревизий). `404` — откатывать нечего, `409` — версия страницы изменилась.

### patch

```json
{
  "base_version": 1,
  "version": 2,
  "ops": [
    {"op": "add_widget", "widget": {"id": "w5", "column": "analytics", "title": "Новый виджет"}},
    {"op": "add_link", "link": {"id": "l16", "from": "n1", "to": "w5"}},
    {"op": "update_widget", "id": "a1", "fields": {"title": "Новый заголовок"}},
    {"op": "update_link", "id": "l3"},
    {"op": "remove_link", "id": "l2"},
    {"op": "remove_widget", "id": "d3"}
  ]
}
```

| Операция | Что делает фронт |
|---|---|
| `add_widget` | добавляет заголовок в блок; содержимое подгрузит по `GET /widgets/{id}` при раскрытии |
| `update_widget` | применяет `fields` (заголовок, ссылка, теги; `tags` заменяются целиком), сбрасывает кэш содержимого и матрицы; если виджет раскрыт, загружает заново |
| `remove_widget` | убирает виджет и все его стрелки |
| `add_link` | рисует новую стрелку |
| `update_link` | применяет `fields` (необязательно) и сбрасывает кэш описания связи |
| `remove_link` | убирает стрелку |

Операции применяются по порядку. Новые виджеты и стрелки сервер должен сразу уметь отдать по `GET`.
