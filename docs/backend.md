# Backend (Python, FastAPI)

Оркеструет остальные сервисы, хранит профили пользователей и готовые страницы, отвечает фронту. Код: [backend/](../backend/).

## Что делает, шаг за шагом

1. В стартовом меню пользователь выбирает компанию из списка банка (`GET /api/companies`) и описывает роль. Фронт шлёт `POST /api/profile`.
2. Бэкенд превращает запись в ключ: `sha1(компания | сфера | регион | метод поиска)`, 12 символов. Опечатки и синонимы одной сферы («закупкки», «снабжение») дают один ключ. Другой метод поиска даёт другой ключ.
3. Профиль кладётся в таблицу `profiles` со статусом `queued`. Если такая страница уже готова и ей меньше `PROFILE_TTL_HOURS` (24 часа), она отдаётся сразу и бесплатно.
4. Фоновый поток бэкенда берёт `queued` профиль и ставит ему `running`.
5. Компания: если введён id вида `U_123` (обезличенные данные банка), по CSV собираются описание для поиска и карточка для аналитики ([companies.py](../backend/companies.py)). Иначе в поиск уходит введённый текст.
6. Строка роли разбирается ([focus.py](../backend/focus.py)): должность выбирает правила решений (по умолчанию финансовый директор), отрасль или тема передаётся как «сфера».
7. `POST news_search/search` с методом из `NEWS_SEARCH_METHOD` возвращает топ-30 новостей и связки.
8. `POST analytics/page` строит из них новости, аналитику и решения.
9. Бэкенд добавляет ко всем id виджетов и связей префикс ключа (так id уникальны между страницами), сохраняет страницу в `profiles.page` и ставит статус `ready`. Любая ошибка попадает в `profiles.error`, статус `failed`.
10. Пока идёт работа, воркер пишет в `profiles` этап (`search` → `rank` → `analysis`) и числа новостей. Фронт раз в 1,5 секунды спрашивает `GET /api/profile/{key}`, при `ready` просит `GET /api/page?profile={key}`.

Без профиля `GET /api/page` отдаёт демо-страницу про Газпром ([backend/demo/seed.json](../backend/demo/seed.json)); открытие карточек и чата доступно, а обработка сообщения просит сначала создать профиль и не меняет демо.

## Выбор метода поиска новостей

Переменная окружения `NEWS_SEARCH_METHOD` (в [.env](../.env.example) и compose): `lexical`, `dense_llm` или `dense_xquad` (по умолчанию). Описание методов: [news-search.md](news-search.md). Неизвестное значение останавливает бэкенд при старте.

## Чат

Открытие чата (`message: null`) сразу возвращает карточку. Сообщения сохранённого профиля обрабатываются асинхронно через Gemma `feedback_intent`; ответ HTTP 202 содержит `operation_id`. Результат с распознанным сценарием, фактическими изменениями и источниками читается через `GET /api/feedback/{operation_id}`. Подробный контракт ниже. Обработчиков по подстрокам «добавь/измени» в рабочем пути больше нет.

# Контракт между фронтом и бэкендом

Все пути начинаются с `/api`, формат — JSON, кодировка UTF-8. В разработке Vite проксирует `/api` на `http://127.0.0.1:8000` (адрес задаётся в [frontend/vite.config.ts](../frontend/vite.config.ts)).

## Как работает страница

1. Фронт запрашивает `GET /api/page` и сразу рисует три блока: только заголовки виджетов и стрелки между ними.
2. Всё остальное подгружается по действиям пользователя и кэшируется:
   - клик по виджету (раскрытие) → `GET /api/widgets/{id}`;
   - «Матрица рисков» → `GET /api/widgets/{id}/risks`;
   - клик по стрелке → `GET /api/links/{id}`;
   - кнопка «Спросить» внизу виджета или в окне стрелки → `POST /api/chat`.
3. Сообщение чата получает HTTP 202 и `operation_id`. Фронт опрашивает `/api/feedback/{operation_id}` и применяет `result.page` либо `result.patch`, добавляя, меняя или удаляя виджеты и стрелки.
4. У страницы есть `version`. Каждый патч увеличивает её на 1. Если `base_version` патча не совпал с версией у фронта, фронт перезагружает `/page` и сбрасывает кэш.

## Схемы

```
Column   = "news" | "analytics" | "decisions"
Widget   = { id, column: Column, title, url?: string, tags?: Tags }   // url — ссылка на оригинал (кнопка «источник» в раскрытом виджете)
Link     = { id, from: <id виджета>, to: <id виджета> }               // стрелка идёт слева направо: news→analytics→decisions
Tags     = { confidence?, source?, industry?, urgency? }                  // см. раздел «Теги»
Company  = { name, okved, role, date }
```

## Теги

Теги лежат в скелете виджета (`tags` в `GET /api/page` и в патчах), поэтому видны и на свёрнутом виджете. Все поля необязательны. Значения в API — английские, подписи на русском подставляет фронт.

| Поле | Значения | Смысл | Где ставится |
|---|---|---|---|
| `confidence` | `reliable` (достоверно), `probable` (вероятно), `possible` (возможно) | степень уверенности в выводе | аналитика, решения |
| `source` | `ai` (ИИ), `alfa` (Альфа), `human` (человек) | чей это анализ | новости (только `alfa` для материалов банка), аналитика, решения |
| `industry` | произвольная строка («Китай», «Автомобилестроение») | отрасль или тема новости | новости |
| `urgency` | `urgent` (срочно), `medium_term` (среднесрочно), `not_urgent` (не срочно) | срочность действия | решения |

Правило происхождения (#26): дословная пользовательская правка и добавленная пользователем новость получают `source: human`; сгенерированный по запросу пользователя вывод остаётся `ai`, а материал банка — `alfa`. Триггер из чата сам по себе не меняет авторство ИИ-текста. В `feedback_state.widget_sources` сохраняются ссылки происхождения; при изменении тегов патч передаёт их целиком (`update_widget`, `fields.tags`).

## Профиль пользователя

Пользователь выбирает в стартовом меню компанию и вводит роль текстом (или сферу анализа). Сервер готовит под них страницу в фоне: поиск по корпусу новостей, отбор и ИИ-анализ. Первый раз это занимает минуты, повторы того же запроса в течение суток берутся из кэша.

`POST /api/profile` с телом `{"company": "…", "role": "…", "region": "…", "company_id": "U_123", "force": false}`:

- `role` обязательно; нужно либо `company`, либо `company_id` (вид `U_` и цифры; такой id можно ввести и в поле `company`);
- `region` необязательно; для `company_id` регион берётся из данных банка;
- текстовые поля до 200 символов, иначе 422;
- `force: true` обходит кэш готовой страницы и ставит новый расчёт в очередь, сохраняя пользовательские правки, источники и исключения. Кэш самого `news_search` остаётся действующим: флаг не обещает повторную загрузку корпуса или новые вызовы LLM.

Ответ: `{"key": "…", "status": "queued|running|ready|failed", "error": "", "cached": false}`. Ключ `key` зависит от компании, сферы, региона и метода поиска. `cached: true` значит, что страница уже была в базе и отдана сразу (статус `ready`, анализ не запускается; тот же кэш на `PROFILE_TTL_HOURS`). `GET /api/profile/{key}` возвращает `{key, status, error, stage, found, selected}` (404, если профиля нет); фронт опрашивает его раз в 1,5 секунды, пока статус `queued` или `running`. `stage` — `search` (формирование запроса и поиск в БД), `rank` (`found` — сколько новостей найдено, идёт отбор), `analysis` (`selected` — сколько новостей отобрано для анализа); `found` и `selected` равны `null`, пока неизвестны. Поиск идёт одним вызовом `news_search`, поэтому `rank` бэкенд отмечает после его ответа, а не во время ранжирования. При `failed` в `error` причина; повторный `POST` ставит профиль в очередь заново.

`GET /api/companies?q=&offset=0&limit=50` (`limit` до 200) возвращает `{"total": n, "items": [{"id": "U_67", "okved_name": "…"}]}` из `df_Uid_data_hack.csv` в порядке файла; `q` — подстрока id или названия ОКВЭД без учёта регистра. 503, если CSV недоступен.

Когда статус `ready`, фронт запрашивает `GET /api/page?profile={key}` (404, если страницы ещё нет). Без параметра `profile` возвращается демо-страница. Ключ профиля фронт хранит в `localStorage`. Если у компании нет карточки банка, `company.okved` равен `"не указан"`. Id виджетов и связей страницы профиля начинаются с `{key}_`.

Ссылка `url` виджета аналитики может вести на страницу PDF Альфа-Банка: `/api/papers/<файл>.pdf#page=N`.

## GET /api/page

Начальный вид страницы.

```json
{
  "version": 1,
  "company": {"name": "ПАО «Газпром»", "okved": "06.20 …", "role": "Финансовый директор", "date": "21 октября 2026"},
  "widgets": [{"id": "n1", "column": "news", "title": "Совет директоров …", "url": "https://…",
               "tags": {"industry": "Газовая отрасль"}}],
  "links": [{"id": "l1", "from": "n1", "to": "a4"}]
}
```

## GET /api/widgets/{id}

Раскрытое содержимое виджета. 404, если виджета нет.

```json
{
  "id": "a1",
  "text": "База 2025 — 38,8 млрд м³ …",
  "src": "Ведомости", "date": "20.10.2026",
  "kpis": [{"value": "1,096 трлн ₽", "label": "новый лимит"}],
  "chart": {
    "type": "line", "unit": "млрд м³", "demo": true,
    "labels": ["2025", "2026", "2027"],
    "series": [{"name": "Оптимистичный", "color": "#7DB800", "values": [38.8, 44, 48]}]
  }
}
```

`src`, `date`, `kpis`, `chart` необязательны. `chart.type` — `line` или `bars`, серий не больше двух.

## GET /api/widgets/{id}/risks

Матрица рисков решения. 404, если виджет не решение или его нет.

```json
{
  "id": "d2",
  "steps": ["Определить долю долга под плавающую ставку."],
  "bank_offer": "процентные свопы … в Альфа-Бизнес",
  "risks": [{"name": "Ставка не снизится", "probability": 3, "impact": 3, "mitigation": "Ступенчатая фиксация."}]
}
```

`probability` и `impact` — целые 1–4 (клетка матрицы 4×4). `bank_offer` — нативное предложение банка, может быть `null`.

## GET /api/links/{id}

Описание связи от ИИ. 404, если связи нет.

```json
{"id": "l1", "from": "n1", "to": "a4", "text": "Корректировка лимита …"}
```

## POST /api/chat — единый вход обратной связи (#26)

```json
{"context":{"type":"page","id":"<profile_key>"},"session_id":null,"message":"Добавь анализ логистики",
 "page_version":1,"request_id":"11111111-1111-4111-8111-111111111111"}
```

`context.type`: `widget|link|page`; `id` — существующий ID блока/стрелки или ключ профиля. `message` — null (открыть чат) либо непустой текст до 8000 символов; `session_id` — до 100 символов; `page_version` — положительное целое. `request_id` — необязательный UUID; повтор того же запроса с тем же UUID возвращает прежнюю операцию, включая повтор после удаления её целевого блока. Другой запрос с этим UUID — 409.

Открытие чата отвечает HTTP 200 прежними `{session_id, reply, patch: null}`. Сообщение сохранённого профиля отвечает HTTP 202:

```json
{"operation_id":"<id>","run_id":"<run_id>","status":"queued","session_id":"<id>",
 "reply":{"text":"Запрос принят. Результат появится после обработки.","basis":[],"followups":[]},"patch":null}
```

Клиент должен опрашивать `GET /api/feedback/{operation_id}` до конечного статуса. Ответ:

```json
{"operation_id":"<id>","profile_key":"<key>","run_id":"<run_id>","session_id":"<id>","status":"completed",
 "created_at":"2026-10-26T12:00:00Z","finished_at":"2026-10-26T12:00:10Z",
 "result":{"scenario":{"kind":"extend","reason":"Запрошена новая тема."},
   "reply":{"text":"Изменения сохранены.","basis":[],"followups":[]},
   "patch":{"base_version":1,"version":2,"ops":[]},"page":{"version":2,"company":{},"widgets":[],"links":[]},
   "changes":[{"kind":"added","type":"widget","id":"<id>","title":"Новый вывод"}],
   "sources":[{"id":"article:123","title":"Источник","url":"https://example.org/news","origin":"news"}]}}
```

`page` в примере сокращена: это полный скелет `GET /api/page`, включая company. Для мутации клиент может заменить им текущую страницу, сбросив кэши деталей; `patch` сохраняется для совместимости обычных изменений. При вопросе `patch/page` равны null, версия не увеличивается. `changes.kind`: `added|replaced|removed`, `type`: `widget|link`. Источники собирает backend из сохранённых ссылок, а не из произвольного списка модели.

Статусы операции: `queued`, `running`, `completed`, `needs_clarification`, `blocked`, `conflict`, `failed`. Последние пять — конечные. В отказе/ошибке `result.error` содержит безопасные `code/message`; `scenario` может быть null, если классификация не завершилась. Конфликт версии до постановки в очередь — HTTP 409 без вызова LLM; конфликт во время обработки — статус `conflict` без публикации. 404 — нет страницы/контекста/операции или операция уже удалена; 422 — неправильный ввод. Демо отвечает просьбой выбрать профиль без LLM и без изменений.

`run_id` может быть null при недоступности журнала: заголовок `X-Trace-Incomplete: true` сообщает об этом, но сама операция сохраняется и выполняется. При нормальной работе он связывает запрос с журналом #29. Неизвестный сетевой результат после сбоя не повторяется автоматически: после старта процесса незавершённые операции получают `failed/interrupted`, пользователь повторяет запрос явно с новым request_id.

### patch

Операции: `add_widget {widget}`, `update_widget {id,fields}`, `remove_widget {id}`, `add_link {link}`, `update_link {id,fields}`, `remove_link {id}`. Добавление содержит публичный скелет элемента; детали доступны обычными маршрутами. `update_widget` инвалидирует детали даже при неизменном заголовке. Сначала удаляются связи, затем блоки; новые блоки добавляются раньше связей. `base_version` должен совпасть с текущей версией, иначе нужна перезагрузка страницы.

## Обработка сценариев, шаг за шагом

1. В одной транзакции блокируется профиль, проверяется версия и request_id, создаются `feedback_operations` и запуск журнала. В payload сохраняются контекст и сообщение: это данные обработки в backend, они не копируются в журнал событий.
2. Фоновый worker по очереди берёт одну feedback-операцию и один профиль. Для одного профиля нет двух одновременно исполняющихся операций; блокировки PostgreSQL не удерживаются во время сетевых/LLM-вызовов.
3. Gemma `feedback_intent` получает сообщение, до 80 заголовков виджетов и 160 связей; выбранный контекст имеет приоритет. Схема проверяет сценарий, существование ID, дословность ручного текста и URL из запроса/выбранного источника. Непонятные и составные команды требуют уточнения, без мутации.
4. `question` вызывает `/reply` с выбранным блоком, связью или ограниченным текстом всей страницы и возвращает реальные ссылки на источники. `extend` вызывает `/refine(kind=topic)` и `/page`, затем добавляет цепочки. `perspective` передаёт старые `page_line/page_region` и новые `line/region`, затем заменяет ИИ-контент, сохраняя ручные блоки, добавленные статьи и необходимые им исходные блоки. Настройки перспективы сохраняются отдельно от исходного ключа профиля.
5. `remove` удаляет целевой блок и только исключительных ИИ-потомков; общий или ручной контент сохраняется. Все висячие связи удаляются. Corpus aid, URL и локальные ID сохраняются как исключения; `/refine` получает показанные/удалённые aid, остальные исключения применяет backend. Удаление стрелки удаляет только стрелку.
6. `link` загружает текст в профиль, вызывает допоиск связанных новостей и анализ. Локальный ID — `user:<uuid>`; таблицы collector не меняются, вымышленного aid нет. Добавленная статья помечается human, выводы — ai. Повтор уже показанной статьи не создаёт дубликат. Явное повторное добавление может снять исключение этой статьи.
7. Правка изолированной новости сохраняет дословный текст как human/possible с отдельным локальным источником и ссылками на оригинал. Правка аналитики, решения, связи или новости с зависимыми блоками требует #28: возвращается `blocked/analytics_dependency_unavailable`, вся страница остаётся прежней. Так же блокируется `proposal`. Для lexical/dense_llm допоиск даёт `blocked/unsupported_search_method`; метод не переключается. Явный refresh (`perspective, refresh=true`) использует обычный `/search` настроенного метода.
8. При изменённом составе входных новостей индексы `pairs` не переиспользуются. `/page` получает до 6000 символов текста каждого источника и сохраняет своё ограничение первых 10 цепочек; остальные пользовательские материалы остаются на странице без обещания нового анализа каждого из них.
9. Перед публикацией повторно проверяется версия. Предыдущие страница и пользовательское состояние сохраняются в `profile_revisions`, публикация и результат операции фиксируются атомарно. При конфликте, ошибке сервисов или пустом результате прежняя страница не меняется.

`profiles.feedback_state` хранит источники и их соответствие блокам, эффективную перспективу, ручные ID и исключения. Актуальные ссылки не восстанавливаются по порядку нового журнала поверх старых блоков. Для старых страниц используется прежний journal; если номера источников не восстановились, поисковая мутация требует обновить профиль (`sources_refresh_required`). После публикации активное состояние очищается от ненужных ссылок; предыдущие варианты остаются в ревизиях.

## Undo и хранение

`POST /api/profile/{key}/undo` с `{"page_version": 3, "target_version": 1}` атомарно восстанавливает страницу и пользовательское состояние, возвращает `{patch,page,changes,scenario}` и создаёт новую версию 4, не возвращает счётчик к 1. Восстанавливаются также исключения и источники; LLM не вызывается. 409 — версия изменилась или профиль пересобирается; 404 — нет профиля или ревизия уже не хранится.

Хранятся последние 20 предыдущих версий. Завершённые feedback-операции, сообщения и результаты удаляются через 7 дней отдельной минутной очисткой; пользовательское состояние и ревизии не зависят от семидневного журнала. Операция без публикации не расходует ревизию. У профиля сохраняется последняя рабочая страница даже при ошибке пересчёта.

## Загрузка URL

[article_fetch.py](../backend/article_fetch.py) допускает только публичные HTTP(S)-адреса на стандартных портах, без учётных данных и управляющих символов. Все разрешённые DNS-адреса проверяются; loopback, частные, link-local, зарезервированные и multicast запрещены. Соединение закреплено за проверенным IP, Host и проверка сертификата TLS используют исходное имя. До трёх перенаправлений проверяются заново, переход HTTPS→HTTP запрещён.

Общий лимит загрузки — 20 с в отдельном завершаемом процессе, включая DNS и медленные HTTP-заголовки; завершение процесса может добавить до 2 с. Ответ — не более 2 MiB, извлечённый текст — 50 тыс. символов. Поддерживаются HTML/plain text без content-encoding; script/style и подобные блоки исключаются, сохраняются исходный/конечный URL и SHA-256. Заголовок берётся из HTML либо имени хоста, дата не выдумывается. Страницы с JS, платным доступом, PDF и обязательным сжатием могут не загрузиться; ошибка не меняет страницу. Никаких cookies, пользовательских заголовков и credentials запрос не пересылает.

Недостающий контракт для #28: отдельная операция `edit|proposal`, которая принимает исходную страницу, карточку/роль/сферу, стабильные источники `{source_id, aid?, title, link, summary, origin}`, целевой блок и дословный пользовательский текст; возвращает пересмотренные блоки/связи и проверяемые ссылки/цитаты с явным списком заменяемых ID. ## Журнал запусков (#29)

Журнал — последовательность наблюдаемых действий и ссылок на доказательства. Промпты, скрытые рассуждения модели, сырые ответы, сообщения чата и финансовые сведения карточки компании в него не записываются.

Как работает, шаг за шагом:

1. `POST /api/profile` атомарно сохраняет профиль и создаёт запуск в `trace_runs`. Ответ и `GET /api/profile/{key}` дополнены `run_id`. Повтор queued/running сохраняет запуск; готовый профиль из суточного кэша возвращает прежний `run_id` и `cached: true`; повтор после ошибки или устаревания создаёт новый запуск.
2. Worker записывает начало и завершение подготовки профиля, поиска, аналитики и публикации. `news_search` добавляет фактические запросы, чтение корпуса, дедупликацию и отбор; `analytics` — обработку источников, решения и проверку. В событиях есть родительские шаги; параллельные ветки различаются по источникам.
3. Backend передаёт `X-Run-ID`, `X-Trace-Parent`, `X-Trace-Capability`, `X-Trace-Incomplete` внутренним сервисам. Capability случайная, в БД хранится только хеш; в публичный ответ capability не попадает. Контекст переносится в пулы потоков отдельно для каждого задания.
4. Сервисы отправляют события в backend по HTTP. Backend единственный пишет `trace_runs` и `trace_events`. События идемпотентны по `(run_id, event_id)`, порядок чтения определяется серверным `seq`, а не часами сервисов. При прямом HTTP-запросе поиска/аналитики/агента сервис создаёт самостоятельный запуск и отдаёт его в заголовке `X-Run-ID`.
5. Ошибка доставки не останавливает расчёт: ответ содержит `X-Trace-Incomplete: true`, а запуск получает `incomplete: true`. Для одного запроса после сбоя доставки дальнейшие удалённые события пишутся в безопасный структурированный резервный лог; максимум две попытки доставки с тайм-аутом 1 с на сетевую операцию. Промежуточные данные при падении процесса могут потеряться: после перезапуска незавершённые running-запуски отмечаются failed/incomplete, профили возвращаются в очередь с новым запуском.
6. Завершённые запуски удаляются каскадно вместе с событиями через 7 дней после завершения. Очистка идёт при старте и раз в минуту отдельным потоком, даже если worker отключён. Активная генерация описаний защищена от удаления. Журнал не заменяет сохранённую страницу.

### Публичный контракт

- `GET /api/profile/{key}/runs` → `{"runs": [{"run_id", "status", "incomplete", "created_at", "finished_at"}]}`; неизвестный профиль — 404. Список включает отдельные обращения чата к этому профилю.
- `GET /api/runs/{run_id}?after=0&limit=100` → `{run_id, profile_key, status, incomplete, created_at, finished_at, events, next_cursor}`. `status`: `queued|running|completed|failed`; неизвестный или удалённый запуск — 404. `after` — неотрицательный курсор, `limit` — 1–200. Следующий опрос передаёт `next_cursor`, пустая страница сохраняет курсор.
- `POST /api/runs/{run_id}/descriptions` → `{run_id, descriptions: {event_id: text}, cached}`. 409 — запуск ещё идёт или описания уже генерируются; 503 — генерация выключена; 502 — ошибка модели/проверки. Повтор успешного запроса возвращает кэш без LLM.

Пример публичного события (необязательные поля могут быть пустыми/null):

```json
{"cursor": 18, "event_id": "0123456789abcdef0123456789abcdef", "span_id": "1123456789abcdef0123456789abcdef", "parent_id": null,
 "section": "news_search", "step": "ranking", "timestamp": "2026-10-26T10:00:00Z", "duration_ms": null,
 "status": "completed", "counts": {"before": 120, "selected": 30}, "queries": [], "source_ids": ["article:123"],
 "widget_ids": [], "error_code": null, "text": "Отбор новостей: завершён. до: 120; отобрано: 30."}
```

Статусы события: `started|completed|failed|cached|skipped`. `counts` содержит только известные значения: `before`, `after`, `duplicates`, `own_removed`, `selected`, `queries`, `notes`, `decisions`, `claims`, `unsupported`, `excluded`, `removed`, `regional`. Примеров сгенерированных поисковых запросов максимум три по 200 символов, URL, адреса почты, похожие на ключи значения и длинные числовые идентификаторы отбрасываются. Ссылки на материалы: `article:<aid>`, `N<aid>`, `alfa:<документ>:p<страница>:t<тезис>`; `widget_ids` связывает публикацию с виджетами страницы. Неизвестные измерения не придумываются; например, длительность отбора без отдельного таймера — null.

`agent`, `model`, `attempt`, `usage` и сами события `llm/gateway` остаются служебными в PostgreSQL. `company_ref` — хеш нормализованного названия или обезличенного ID, без копии банковской карточки. Открытие чата без сообщения не запускает обработку; демо-страница сохраняет прежний режим без БД. Постановка сообщения профиля в очередь создаёт отдельный запуск и добавляет `run_id` в ответ чата; результат обработки читается через `/api/feedback/{operation_id}`.

### Служебные маршруты и безопасность

`POST /internal/trace/runs` принимает `{kind: news_search|analytics|agents, company_ref: <sha256>}` и возвращает `{run_id, capability}`. `POST /internal/trace/runs/{run_id}/events` принимает `{"event": <строгая схема Event>}`, а `/finish` — `{status: completed|failed, incomplete}`. Запись и завершение требуют `X-Trace-Capability` (403 при неверном значении); неизвестные поля/модели/счётчики отвергаются (422).

Маршруты `/internal` недоступны через frontend/nginx. Backend-порт опубликован только на loopback; создание запуска доверяет внутренней Docker-сети. Не публикуйте этот порт наружу без отдельной аутентификации. Публичный API журнала использует ту же модель доступа, что существующий API профилей; авторизация по пользователям здесь не добавляется.

### Описания Gemma и расход

Без LLM каждый шаг сразу получает фактический шаблонный текст. По запросу `trace_description` выбирает только `compact|detail` и категории фактов для не более 40 завершённых публичных событий. Все непустые категории обязательны; произвольный текст, неизвестные ID и дубли отвергаются. Код вставляет реальные числа, примеры запросов и ссылки. Остальные события сохраняют обычные тексты. События LLM/генерации описаний не передаются на описание повторно.

`TRACE_AI_ENABLED=false` по умолчанию; для включения оператор должен подтвердить валюту `usage.cost` и остаток общего лимита 500 ₽/сутки. Флаг должен совпадать у backend и agents (Compose делает это автоматически). `AGENTS_URL` — адрес сервиса агентов, по умолчанию `http://agents:8000`. Журнал хранит стоимость в единицах шлюза, не объявляет её рублями и не вводит общий бюджетный ограничитель. Неизвестная стоимость — null, а не бесплатный вызов. Замер: [backend/benchmarks/run-journal.md](../backend/benchmarks/run-journal.md).
