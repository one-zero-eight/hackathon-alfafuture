# Распознавание обратной связи: датасет и протокол замера

Раздел: agents
Дата: 2026-10-26 · Версия: backend/feedback-orchestration (рабочее дерево)

## Что измеряем

Гипотеза: разрешённая Gemma распознаёт намерение пользователя дешевле и быстрее тяжёлой модели и достаточно точно выбирает семь сценариев плюс уточнение. Модель выбрана пользователем; гипотеза качества/стоимости ещё не подтверждена живым измерением.

## Метрика

- Macro-F1 по восьми классам: среднее `2*TP/(2*TP+FP+FN)`. Цель >=0,90, больше лучше.
- `unintended_mutations`: сколько эталонных question/clarify попало в extend/perspective/edit/remove/link/proposal. Цель 0, меньше лучше. Это ошибка маршрутизации, не число фактически изменённых страниц: оценочный скрипт не вызывает backend.
- Медиана времени одного вызова, мс; суммарные токены и известный `usage.cost` в единицах шлюза, неизвестная стоимость отдельно. Меньше лучше. Рубли без подтверждённой валюты не вычисляются.

## Данные и окружение

[feedback-intents.json](feedback-intents.json): 80 примеров, по 10 на question, extend, perspective, edit, remove, link, proposal, clarify. Контекст: одна новость, вывод, решение и связь; выбираемый элемент меняется по примеру. Есть русский/английский текст, опечатки, составные и неоднозначные команды, гипотетические вопросы об удалении. Эталонные метки подготовлены при реализации; независимая разметка человеком не проводилась. Примеры не включаются в промпт модели.

Локально: Python 3.13, uv workspace, Docker Desktop Linux (20 CPU, около 61,2 GiB RAM). GPU и реальные эмбеддеры для проверки схемы не используются. Живой сервис организаторов не вызывался: доступный бюджет и валюта ещё не подтверждены.

Схема и протокол готовы. Фикстурные ответы не доказывают качество модели, достижение целевого F1 или соблюдение бюджета 500 ₽/сутки. Живой результат нужен отдельно до приёмки #26. Другие модели не сравнивались.

## Ограничения

80 искусственно составленных запросов, по одному фиксированному контексту, нет независимой разметки и распределения реального трафика. Многоходовая беседа не оценивается: session_id здесь идентификатор ответа, а не долговременная история разговора. При --limit меньше 80 оценивается только выбранная часть; качество на ней не подтверждает цель по всему набору. Ошибки HTTP могут скрывать уже потраченный usage, поэтому после первой ошибки замер останавливается; для полного расхода сверяйте журнал gateway сервиса agents. Лимит стоимости проверяется между запросами: один вызов способен его превысить; это не ограничитель общего бюджета приложения.

## Как воспроизвести

```bash
uv sync --all-packages
# Только проверка датасета, без сети и расхода:
uv run python -m agents.benchmarks.feedback_intents
uv run pytest agents
# Только после подтверждения валюты шлюза, дневного остатка и разрешённого лимита замера:
AGENTS_URL=http://localhost:8001 uv run python -m agents.benchmarks.feedback_intents --live --max-cost <лимит-в-единицах-шлюза> --limit 80
```

Живой agents должен иметь настроенные LLM_BASE_URL и LLM_API_KEY. Сохраняйте результат скрипта и параметры промпта/модели в следующем датированном прогоне этого отчёта; неизвестный расход не объявляйте бесплатным.
