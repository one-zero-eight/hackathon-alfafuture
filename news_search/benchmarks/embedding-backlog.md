# Холодный поиск: догоняющее встраивание корпуса и суточный поток новостей

Раздел: news_search
Дата: 2026-10-26 · Версия кода: локальные образы стека, рабочая копия на ветке `news_search/refine` (1fc602b); сборка образов отдельно не проверялась · Автор: Goober-nation (с ИИ-агентом)

## Что измеряем
1. Сколько занимает первый поиск `dense_xquad` после простоя коллектора и из чего складывается время.
2. Сколько новостей в сутки приходит из выбранных источников, то есть сколько нужно встраивать каждый день.

Гипотеза: время холодного поиска определяют не LLM, а встраивание bge-m3 новостей, которых ещё нет в `vectors_bgem3.npz`; оно идёт синхронно внутри запроса `/search`.

## Метрика
- Время этапов, с (меньше лучше): по меткам `call`/`result` в логах `agents`, по времени записи `vectors_bgem3.npz` и по ответу `/search`.
- Скорость встраивания, с на новость: время этапа встраивания / число новых векторов (меньше лучше).
- Поток новостей, шт./сутки: `count(*)` по `articles.published_at::date` (строки после дедупликации и отбраковки коллектора).

## Данные и окружение
- MacBook, Docker Desktop: в контейнере нет GPU, bge-m3 считается на CPU (`sentence_transformer` выбирает cuda → mps → cpu), `max_seq_length=128`, батч 64.
- Корпус: 133 073 новости в окне `CORPUS_DAYS=365` (136 954 всего); в кэше векторов до замера 122 691 — около 10 000 новостей без вектора (коллектор стоял, затем догнал ленты).
- Коллектор перезапущен с `LLM_ENABLED=false` (тегирование и геотеги выключены, сбор идёт).
- Профиль: «Вкусно — и точка», сфера «Закупки», регион «Москва», метод `dense_xquad`, один прогон.
- LLM: DeepSeek-V4.1-Flash для `queries`, `needs`, `hyde`.

## Сравниваемые методы
| Метод | Чем отличается | Параметры |
|---|---|---|
| Холодный поиск | кэш векторов неполный, результата в кэше нет | `dense_xquad`, N_DENSE=100, TOP_CAND=150 |
| Повтор того же запроса | результат из кэша (`CACHE_TTL` 24 ч) | — |

## Вывод
- Холодный поиск на 92 % состоит из встраивания догоняющего хвоста; три вызова LLM — ~2,5 мин и идут последовательно, хотя независимы.
- При прежнем потоке ~2k новостей в сутки встраивание на CPU — ~8 мин в сутки; при 6–10k — 25–40 мин. Это нормально для фонового встраивания каждые 10–15 мин, но не внутри запроса.
- Предложения (код не менялся, нужен согласованный план): фоновое встраивание при старте и по таймеру с сохранением частями; параллельные `queries`/`needs`/`hyde`; встраивание на хосте через MPS для догонки.
- Векторы привязаны к `articles.id`: переносить `vectors_bgem3.npz` можно только вместе с дампом той же базы.

## Ограничения
- Один прогон, один профиль; скорость MPS на хосте не измерена.
- Код стека — локальная ветка, а не текущий `origin/main` (в нём уже есть усиление региона и раздельные флаги тегирования и геотегов коллектора).
- Всплеск 20–23.10 не объяснён: возможно, расширение `sources.json` или догрузка истории, а не реальный суточный поток. Google News с 24.10 не дал ни одной новости — причина не проверена.
- Поток считан по дате публикации; по `collected_at` картина может отличаться.

## Как воспроизвести
```bash
docker compose --env-file .env -f docker/compose.yaml up -d --build
curl -s -X POST localhost:8002/search -H 'content-type: application/json' -d '{"company":"Вкусно — и точка","line":"Закупки","region":"Москва"}'
docker compose --env-file .env -f docker/compose.yaml logs agents | grep -E '"event": "(call|result)"'
docker compose --env-file .env -f docker/compose.yaml exec news_search python -c "import numpy as np; print(len(np.load('/data/vectors_bgem3.npz')['ids']))"
```
Поток по суткам:
```sql
select published_at::date d, count(*) from articles where published_at > now() - interval '22 days' group by 1 order by 1;
```
